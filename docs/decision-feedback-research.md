# 원격 승인·거절 피드백 조사 — 2026-09-21

## 범위와 현재 결론

사용자 요청은 처리 시간 조사 후 안심할 수 있는 UI를 연구하는 것이다.
이번 변경은 CI 계측과 설계안이며, 아래 승인·거절 UI는 아직 구현하지 않았다.
별도로 요청한 진단 로그 파일 저장과 릴리스 노트 개선은 구현 범위다.

필요한 피드백은 세 가지다: **내 선택이 입력됐는지**, **지금 무엇을 기다리는지**,
**PC가 실제로 어떤 결과를 확인했는지**. 세 가지를 한 성공 메시지로 합치면 안 된다.

## 현행 코드 관찰

- `ui/src/useController.ts`: 입력 즉시 `busy=decision`으로 중복 입력을 막지만,
  공통 문구만 표시한다. bridge 응답 후 notice는 null이다.
- `ui/src/RequestPanel.tsx`: authenticating/waiting/sending/awaiting_outcome 문구는
  있으나, 완료되어 요청이 사라지면 빈 목록으로 돌아간다. 선택한 승인/거절과
  결과를 이어서 보여주는 영수증 형태의 피드백은 없다.
- `NativeRequestCoordinator.changed()` → `DeviceStatePlugin` → `watchRequests()`는
  실제 상태 변경 시 빈 이벤트로 새 스냅샷을 요청하도록 설계됐다. **2026-09-24 정정:**
  1.5.0까지는 이 구독이 한 번도 동작하지 않았다. `device-state` 플러그인에 ACL 권한이
  없어 화면의 구독이 거부됐고 `useController`가 그 거부를 삼켰다. 그래서 화면은 5초 간격
  조회로만 새 요청을 알았고, 실기에서 알림 뒤 카드가 3.2초 늦게 그려졌다. 다음 판은
  구독·해제 두 권한만 Android에 열어 이 경로를 되살렸다.
- `controller-runtime/src/phone_history.rs`: 결과는 인증된 PC 결과를 보존하지만
  요청 UI locator와 history delivery ID가 다르다. 배열 마지막 항목이나 시간 근접성으로
  방금 누른 요청의 결과를 추정하면 다른 요청의 결과를 잘못 붙일 수 있다.
- `NativeRequestRegistry`는 갱신 시 locator를 바꿀 수 있다. 후속 구현은 UI의
  임시 request ID를 장기 식별자로 쓰지 말고 네이티브에서 전체 binding/발급 시각에
  묶인 읽기 전용 receipt를 제공해야 한다. 권한 판단과 재전송은 기존 네이티브 소유다.

## 계측 구간

기존 정확 커밋 `edfeeb204694ea4ffc1fed411247e9bbcc711729`의
[Windows CI 35546407422](https://github.com/115dkk/Windows_UAC_Remote_Controller/actions/runs/35546407422)
artifact에는 `nativeHoldMillis=115011`이 있다. 이것은 갱신 시험을 위한 **의도적
115초 대기**이며 승인·거절 지연이 아니다. 기존 proof에는 decision latency가 없었다.

`tools/ci-phone-fixture/src/session.rs`에 같은 프로세스의 monotonic clock을 사용한
두 구간을 추가했다. `windows-full-pairing-lab.mjs`가 실제 일치하는 signed Denied 결과와
범위 내 정수 계측값을 요구하고 proof에 넣는다.

1. 서명 시작 → 같은 요청의 PC 서명 결과 검증 완료.
2. 전송 큐 진입 직전 → 같은 결과 검증 완료.

실제 Windows 요청 취소(`ERROR_CANCELLED`) 및 대상 프로그램 미실행 검사는 기존대로
별도 통과해야 한다. software phone, 동일 러너 중계를 사용하는 CI 표본이므로 실제
Android 본인 확인·무선망·버튼 입력·화면 그리기 시간으로 일반화할 수 없다.
단일 표본으로 평균이나 p95를 제시하지 않는다. 승인 경로는 자동 승인 권한을
추가하지 않았으며 기존 사용자 실기 시험과 별개다.

### 첫 유효 표본

[CI 35581683195, 두 번째 실행](https://github.com/115dkk/Windows_UAC_Remote_Controller/actions/runs/35581683195/attempts/2),
커밋 `816facce4b780e31868e6590344637f8bcbd2a9b`에서 거절 서명 시작부터
같은 요청의 PC 서명 결과 검증까지 **271.329ms**, 전송 큐 직전부터는
**271.275ms**를 측정했다. 실제 Windows 취소와 대상 미실행 검사도 통과했다.
표본은 1건이며, Android·인증·무선망·화면 표시 시간은 포함하지 않는다.
약 100ms의 즉각 반응 기준을 넘지만 1초 이내여서, 이 표본은 즉시 선택 표시와
유지되는 결과 카드를 뒷받침한다. 의도적으로 로딩을 늘리거나 평균·p95를
추정할 근거는 아니다. 첫 실행은 등록 연결 종료에서 실패해 표본에서 제외했다.

성공한 proof의 정확한 GitHub artifact ID는 `10631222508`이다. 같은 이름의
첫 실패 파일(`10631300739`)도 남아 있으므로 이름만으로 내려받지 않는다.

## 제안하는 UI 상태

| 시점·실제 상태 | 사용자에게 보일 내용 | 다음 동작 |
| --- | --- | --- |
| 승인 입력 직후, 본인 확인 전 | `승인을 선택했습니다` / `본인 확인을 진행하십시오.` | 기존 시스템 인증창, 중복 승인 차단 |
| 거절 입력 직후 | `거절을 선택했습니다` / 실제 큐가 진행되면 `PC로 전송 중입니다.` | 중복 입력 차단 |
| 전송 완료, PC 응답 대기 | `PC의 처리 결과를 기다리고 있습니다.` | 화면은 떠날 수 있음, 재전송 아님 |
| 같은 요청의 인증된 Approved/Denied | `PC에서 승인했습니다` 또는 `PC에서 거절했습니다` | 체크/거절 아이콘, `확인` 버튼 |
| 인증 취소 | `본인 확인을 취소했습니다` | 네이티브가 여전히 허용할 때만 새 선택 |
| Failed/Expired/Cancelled | 각각 처리 실패/요청 만료/PC에서 취소 | 결과에 맞는 다음 행동 |
| 응답 지연 또는 연결 단절 | `아직 PC의 결과를 확인하지 못했습니다.` | 연결 상태 확인, 결과 조회만; 자동 재전송 금지 |

입력 확인은 네트워크 응답을 기다리지 않고 다음 프레임에 표시한다(목표 100ms 이내).
짧은 작업에 의도적 지연을 넣지 않는다. 길어지면 실제 전송/PC 응답 단계와 연결 상태를
보여준다. 경과 시간에 따른 문구 변경은 작업 완료 비율을 뜻하지 않으며 가짜 퍼센트나
성공 체크를 쓰지 않는다. 느린 상태 안내 시점은 향후 실제 Android 표본 분포로 조정한다.

결과는 작은 자동 소멸 토스트만으로 끝내지 않는다. 요청 위치의 결과 카드에 두고
사용자가 `확인`하거나 다음 요청을 선택할 때 정리하는 안을 우선한다. 단, 원문 표시
허가가 끝난 프로그램명·경로를 붙잡지 않는다. 유지할 것은 body-free 선택/결과/시각이다.
서명된 결과도 누가 직접 PC에서 선택했는지까지 증명하지 않으므로 `내가 처리했다`는
단정 대신 **내가 선택한 동작**과 **PC가 확인한 결과**를 구분한다.

접근성: 텍스트+아이콘을 함께 사용하고 `role=status`로 단계/결과를 한 번 알린다.
진동은 보조수단이며 시스템 설정을 따른다. 강제 전체화면·반복 애니메이션 없이 기존
카드와 디자인 토큰을 사용한다. 작은 화면, 200% 글자, 키보드, TalkBack, 알림 거절,
잠금/복귀/프로세스 재생성, 중복 입력과 다른 요청의 동시 완료가 후속 검증 대상이다.

검토 방식은 소스 기반 인지적 walkthrough다. 실제 사용자 시험이나 UI 개선 완료
판정이 아니다. 승인·거절 피드백 구현 전에 request→receipt 연결을 보안 검토해야 한다.
