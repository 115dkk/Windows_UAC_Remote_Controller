# ADR 0049: A phone's keys are judged by what its secure hardware signed, not by how the phone started

Status: implemented source with unit coverage and a symbolic model. Not yet
seen on a real unlocked or owner-signed phone: the Rust tests use synthetic
software-signed descriptions and the model is symbolic. The premise that
secure hardware keeps its key policy after the bootloader is unlocked is a
stated assumption, not something this change measures.

## Evidence

The user asked on 2026-11-14 that a rooted phone be allowed to connect once it
proves the same integrity a phone that is not rooted proves, and said that
refusing rooted phones is the easy choice for a developer and not a good one.

One line did the refusing. `root_of_trust` in
`crates/android-attestation/src/description.rs` rejected every key whose
attestation did not say `deviceLocked = true` and `verifiedBootState =
Verified`. The README gave the reason as the PC checking the phone's hardware
key, so the first question was whether that check needs the boot state at all.

The sources below were read on 2026-11-14. ROOT read items 2, 3 and 7 and the
`hardwareEnforced` sentence of item 1 again from the page itself; the rest are
as the research agent quoted them from the files named.

1. The attestation has two lists. `hardwareEnforced` is "collected or
   generated by code in the secure hardware and is not controlled by the
   platform". `softwareEnforced` "can be trusted as long as the device is
   running an operating system that complies with the Android Platform
   Security Model (that is, the device's bootloader is locked and the
   verifiedBootState is Verified)".
   [Key and ID attestation](https://source.android.com/docs/security/features/keystore/attestation)
2. A key in the trusted execution environment is "secure as long as the TEE is
   not compromised". The condition names the TEE, not the operating system.
   Same page, SecurityLevel values.
3. The boot state is itself a hardware-reported field with a defined value for
   an unlocked phone: Unverified means "the device's bootloader is unlocked, so
   a chain of trust cannot be established. The device can be freely modified,
   so the device's integrity must be verified by the user out-of-band. In this
   state the verifiedBootKey field contains 32 bytes of zeroes." SelfSigned is
   "same as Verified, except that the verification was done using a root of
   trust configured by the user". Failed gives "no guarantees about the
   contents of the other RootOfTrust fields". Same page.
4. Authentication per use is enforced inside secure hardware. With
   `USER_SECURE_ID` present and `AUTH_TIMEOUT` absent, "update() and finish()
   must receive a HardwareAuthToken with Tag::USER_SECURE_ID value in userId
   or authenticatorId fields, and the current operation's operation handle in
   the challenge field", and the tags "must be hardware-enforced". The token
   is authenticated with a per-boot key that "must never be made available
   outside the TEE".
   [Tag.aidl](https://android.googlesource.com/platform/hardware/interfaces/+/refs/heads/main/security/keymint/aidl/android/hardware/security/keymint/Tag.aidl),
   [Authentication](https://source.android.com/docs/security/features/authentication)
5. The same file says where that stops: "Password authentication does not
   provide proof of presence to either TEE or StrongBox, even if TEE or
   StrongBox does the password matching, because password input is handled by
   the non-secure world, which means an attacker who has compromised Android
   can spoof password authentication." Tag.aidl, `TRUSTED_USER_PRESENCE_REQUIRED`.
6. The application identity "cannot be hardware-enforced"; the keystore daemon
   fills it in from the caller's UID. The operating-system version and the
   system and vendor patch levels are read "from the system property" by the
   Android-side KeyMint service and handed to secure hardware once per boot;
   only the boot patch level is specified as coming from the bootloader.
   Tag.aidl, `ATTESTATION_APPLICATION_ID`, `OS_VERSION`, `OS_PATCHLEVEL`,
   `VENDOR_PATCHLEVEL`, `BOOT_PATCHLEVEL`.
7. An approved way to show what is signed on a display the operating system
   does not control exists as a key property
   (`TRUSTED_CONFIRMATION_REQUIRED`, Android Protected Confirmation). This
   product's keys do not ask for it, and the verifier refuses a description
   that carries it. Attestation page, `trustedConfirmationReq`.
8. Keys are bound to the root of trust: "If the public key is changed to allow
   a different system image to be used or if the lock state is changed, then
   all of the IKeyMintDevice-protected keys created by the previous system
   state must be unusable". Unlocking and locking both erase user data.
   [IKeyMintDevice.aidl](https://android.googlesource.com/platform/hardware/interfaces/+/refs/heads/main/security/keymint/aidl/android/hardware/security/keymint/IKeyMintDevice.aidl),
   [Device state](https://source.android.com/docs/security/features/verifiedboot/device-state)
9. Google's own statement of what a chain to its root means carries no boot
   condition: "Your key is in hardware that Google believes to be secure; and
   it has the properties described in the attestation certificate." Its
   verifier library asks for Verified and locked only "if you're verifying the
   integrity of the device that produced the attestation".
   [Key attestation guide](https://developer.android.com/privacy-and-security/security-key-attestation),
   [android/keyattestation](https://github.com/android/keyattestation)
10. A published standard already verifies Android key attestation without the
    boot state. The WebAuthn `android-key` procedure checks the signature, the
    public key, the challenge, that `allApplications` is absent, and that
    `origin` is generated and `purpose` is sign, using "only the teeEnforced
    authorization list if the RP wants to accept only keys from a trusted
    execution environment". RootOfTrust is not mentioned in it.
    [WebAuthn Level 3, Android Key Attestation](https://www.w3.org/TR/webauthn-3/#sctn-android-key-attestation)
11. The published analysis of this exact arrangement reaches the same line. For
    an application that signs with a hardware key and whose server verifies key
    attestation, "a root attacker cannot easily compromise the system [...] she
    has similar capabilities as a non-root attacker, and she could thus attempt
    to exploit confused deputy problems via UI attacks", and each attempt needs
    "the user to touch the fingerprint sensor once".
    [Bianchi et al., Broken Fingers, NDSS 2018](https://s3.eurecom.fr/docs/ndss18_fingerprint.pdf), sections V and VI
12. The tools that make a rooted phone look locked rewrite the field the old
    check read. Tricky Store "will hack the leaf certificate by default": the
    key stays the hardware's, the module replaces the root of trust with
    locked and Verified and signs the leaf again with the private key of a
    `keybox.xml` the user supplies. Its other mode makes the key pair in
    software and signs a whole description. Either passes as a Google-rooted
    chain until that keybox is revoked. Google states that leaked attestation
    keys "only affect the older provisioning mechanism" and that devices
    launching with Android 16 support only remote provisioning.
    [TrickyStore README and `CertHack.java`](https://github.com/5ec1cff/TrickyStore),
    [Key attestation guide, revocation policy](https://developer.android.com/privacy-and-security/security-key-attestation#certificate_status)
13. GrapheneOS Auditor, which exists to verify the device and not a key,
    accepts Verified or SelfSigned with an allow-listed boot key and refuses an
    unlocked bootloader. It is the precedent for the `Owner` class and the
    counterexample for anyone reading this ADR as a statement about device
    integrity.
    [AttestationProtocol.java](https://github.com/GrapheneOS/Auditor/blob/main/app/src/main/java/app/attestation/auditor/AttestationProtocol.java)

Items 10 to 13 are as the second research agent quoted them; ROOT did not open
those pages again.

Not found in any primary source: a sentence saying that unlocking the Android
bootloader leaves the firmware of the trusted execution environment under the
chip's own secure boot. The Android documents separate ordinary unlocking from
unlocking the "critical sections" needed to reach the bootloader, and the
chip vendors root the secure-world chain in ROM, so it follows on the devices
those documents describe. It is device-specific and is treated here as a
premise.

## What the PC relies on, and who vouches for it

| # | What the PC relies on | Where it is in the evidence | Who stands behind it | Does the boot state change that? |
| --- | --- | --- | --- | --- |
| 1 | Each private key was made inside secure hardware and cannot leave it | `origin = generated`, both security levels TEE or StrongBox, hardware list | Secure hardware | No |
| 2 | The approval key signs only after secure hardware checks a credential or biometric for that one operation | `userAuthType` present, `noAuthRequired` and `authTimeout` absent, hardware list | Secure hardware | No |
| 3 | Three distinct sign-only P-256 keys; denial and transport need no authentication | Hardware list, three chains | Secure hardware | No |
| 4 | The evidence was made for this ceremony | Challenge inside the signed description | Secure hardware | No |
| 5 | The attester is genuine | Chain to the pinned Google roots, exact profile, revocation list | The PC's own check | No |
| 6 | The keys belong to this application's release build | `attestationApplicationId`, software list | The phone's operating system | It is the operating system's own statement |
| 7 | Operating-system version and patch floors | Hardware list, but handed in from system properties | The phone's operating system | It is the operating system's own statement |
| 8 | Who presented the credential, and what the screen showed while they did | Nowhere in the evidence | The phone's operating system and application | Not attested on any phone |

Rows 1 to 5 are everything an accepted approval rests on cryptographically:
that the signature came from an enrolled key which cannot be copied and which
secure hardware will not use without an authentication for that signature. A
rooted phone proves them with the same fields, the same signatures and the
same chain as any other phone. That is the equal integrity the user asked
for, and it is provable.

Rows 6 and 7 are checked for every phone and were never hardware facts. On a
manufacturer-verified phone the operating system making those statements is
the manufacturer's image. On a locked phone with an owner-installed key it is
an image signed with that key, and the bootloader will load no other. On an
unlocked phone it is whatever is installed.

Row 8 is proved on no phone. A locked bootloader does not prove it; it only
says that the operating system which could lie about it is the manufacturer's.

So the only thing the old refusal bought was an answer to "whose operating
system is this", and it bought it by refusing the owner's own.

## Decision

**The boot state is classified, not required.** `root_of_trust` returns a
`BootAssurance`:

| `deviceLocked` | `verifiedBootState` | Result |
| --- | --- | --- |
| true | Verified | `Manufacturer` |
| true | SelfSigned | `Owner` |
| false | Verified, SelfSigned or Unverified | `Unverified` |
| true | Unverified | refused: defined nowhere |
| any | Failed | refused: the hardware says the image did not pass |
| any | any other value | refused: not guessed at |

An unlocked bootloader is `Unverified` whatever it reported for this start,
because the next start may load any image. A locked phone must name a
non-empty boot key and boot hash. An unlocked one need not: its key is
zeroes, and before the interface fixed the length it could be shorter or
absent (the VTS comment says behaviour on unlocked devices "isn't specified in
the HAL interface specification" for that level), so absence is not held
against it.

**Every other check is unchanged and is the same for every class.** The
challenge, hardware level, purpose, curve, origin, authentication policy per
role, application package, signing-certificate set, minimum application
version, operating-system and patch floors, chain profile and revocation
status apply to an unlocked phone exactly as before. The test
`an_unlocked_or_owner_signed_phone_is_held_to_every_other_check` walks them.
The floors in rows 6 and 7 stay because dropping them for some phones would be
a second policy, and because an honest owner's phone reports them truthfully.

**A bundle carries the least vouched-for class of its three keys.** Three
chains are not proof of one phone (ADR 0017), so one key from an unlocked
phone makes the bundle `Unverified`.

**The PC's owner is shown the class on the protected comparison screen and is
the one who vouches for the operating system.** When the class is not
`Manufacturer`, the six-digit comparison screen adds one sentence:

- `Unverified`: this phone's bootloader is unlocked; if you did not unlock it
  yourself, press ESC to stop.
- `Owner`: this phone runs an operating system that is not the
  manufacturer's; if you did not install it yourself, press ESC to stop.

This is the "out-of-band" verification the attestation page assigns to the
user, placed at the one moment the owner is already deciding whether to trust
this phone, on a screen unelevated software cannot draw over. The class
travels as one byte in the comparison frame between the service and the
renderer and is not otherwise stored. No later decision reads it.

**The threat model is stated the same way on both sides.** A phone whose root
is already in an attacker's hands is outside it, as a PC whose SYSTEM or
kernel is already in an attacker's hands is. That was always true of a locked
phone with an exploited kernel; the refusal hid it by pretending the boot
state answered it.

## What an unlocked bootloader does change

Someone holding an unlocked phone can replace its operating system without
erasing it, and the hardware will not tell the difference: the root of trust
is the same zeroes for every image, so the enrolled keys stay usable under
the replacement. A replaced operating system can record the lock-screen
credential the next time it is entered and present it to secure hardware
itself (evidence 5). On a locked phone the same result needs an exploit.

Nothing the PC can verify closes this, and the product does not claim to. It
is stated in the README, and the comparison screen asks the question that
catches the one case the owner can catch: a phone they did not unlock.

A locked phone with an owner-installed key does not have this gap. Its
bootloader loads only images signed with that key, and evidence 8 makes the
enrolled keys unusable under any other key or lock state for as long as they
are enrolled.

## The proof

`security/tamarin/HardwareKeyEvidence.spthy` models the phone's operating
system as the attacker. It sees every output, chooses every request to secure
hardware, fills in the application identity, picks the bytes to sign and
decides what the screen shows. The PC rule accepts every boot state. Under
those conditions the model requires:

- `enrolled_approval_key_is_hardware_made_with_per_use_authentication`
- `hardware_held_private_keys_stay_secret`
- `accepted_approval_needs_hardware_authentication_for_that_signature`
- `one_hardware_authentication_signs_at_most_once`
- `unlocked_phone_enrolls_and_approves_trace`, an honest trace with the boot
  state fixed at unverified, so the universal lemmas are not vacuous there
- `authentication_is_not_bound_to_what_the_screen_showed`, a trace in which an
  accepted approval was authenticated while the screen showed something else.
  It is required to exist. It is the limit in row 8, written down as a checked
  fact instead of left out.

No universal lemma mentions the boot state, which is the point: the
conclusions hold for every value of it.

Two broken copies must fail. `unchecked-key-attestation` stops checking the
signature of secure hardware on the approval key's description.
`approval-key-without-authentication` lets the PC enroll a key with no
authentication as the approval key. Each must falsify the first and third
lemmas with an actual trace.

The model's premises are that secure hardware follows its key policy in every
boot state, that a certified attestation key has not left its hardware, and
that signatures are unforgeable. It does not model who presented the
credential. It is a symbolic contract and proves nothing about a particular
phone's hardware.

## What the old refusal cost

It turned away owners who had done nothing but choose their own operating
system, and it did not stop the people it was aimed at. A rooted phone that
wants to look locked runs a module that rewrites the boot state in its
attestation and signs the result with a leaked attestation key (evidence 12),
and such a phone passed the old check until that key was revoked. An owner
refused by the PC had a reason to install one. Once the leaf is signed by a
leaked key, every field in it is the module's word and not the hardware's, and
in the module's other mode the key itself is software. That is the one
arrangement in which rows 1 and 2 can be false, so the refusal gave honest
owners a reason to adopt the only configuration that breaks what the PC
actually relies on. An owner whose unlocked phone is accepted as it is has no
reason to. Revocation (row 5) is the defence against a leaked key, before and
after this change.

## Alternatives rejected

- **Keep the refusal.** It answers a question no approval depends on.
- **Accept only locked phones with an owner-installed key.** It is the
  strongest class a rooted phone can have, and few phones can be re-locked
  with a custom key. The request was about rooted phones as they are.
- **Require a biometric-only approval key on unlocked phones.** It would
  refuse people who use a PIN, which this product decided against at the
  start, and it does not bind the authentication to what the screen showed.
- **Require Android Protected Confirmation.** It is the one mechanism that
  would prove row 8. Only Pixel phones implemented it, and their device trees
  stopped building it during Android 15 (the Pixel 9 tree at
  `android-15.0.0_r1`, the Pixel 6 to 8 trees at `android-15.0.0_r6`). The API
  is not deprecated, but nothing sold today is known to answer it.
- **Detect root inside the application.** An operating system that would lie
  to the PC would lie to the application first.
- **Store the class in the device registry and label the phone list.** No
  later decision would read it. It can follow if a label proves useful.

## Limits

Unit tests cover the classification, the unchanged checks, the bundle rule
and the frame byte. No real unlocked or owner-signed phone has been paired.
Whether a given manufacturer's secure hardware still issues attestations
after its bootloader is unlocked is not known here, and neither is whether
Google's remote provisioning service issues certificates to a phone that
reports itself unlocked; a phone that gets no attestation will fail as it did
before, at key generation or at the chain check. For Samsung in particular
there is no published attestation from an unlocked Galaxy to compare with,
and One UI 8 is reported to have removed bootloader unlocking altogether.
