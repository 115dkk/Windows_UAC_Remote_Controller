# 초기 설계 보안 검토

검토일: 2026-09-08

대상: `docs/FEASIBILITY.md`, `docs/IMPLEMENTATION_PLAN.md`

상태: **제품 코드 없는 정적 설계 검토 / 중요 설계 조건 미해결**

후속 사용자 결정: 이 초기 검토 이후 자격 증명형은 스마트폰 직접 입력이 적절하면 지원하고 무리가 있는 유형은 무시하기로 했다. 이미 SYSTEM/커널이 침해된 상태는 위협 모델에서 제외하기로 했다. 아래 SR-08의 범위 합의는 해소되었으며, 당시의 초기 검토를 이력으로 보존한다. 나머지 구현·실증 게이트가 해결되었다는 뜻은 아니다.

## 범위와 판단의 한계

보안 감사관 하위 에이전트가 초기 두 문서의 내용을 읽고 위험한 해석과 누락된 계약을 보강했다. 수정 범위는 이 보고서를 포함한 세 문서뿐이다. 파일 열람과 `apply_patch` 문서 수정만 수행했다. 빌드·테스트·lint·실행 검증·UAC 조작·키 생성·기기 테스트·서비스 설치는 하지 않았고, 추가 에이전트도 생성하지 않았다. 실행 검증은 최상위 에이전트만 수행한다.

이 보고서의 발견은 구현 코드에서 재현한 취약점이 아니라 **현 설계가 악용될 수 있는 경로 또는 아직 입증하지 못한 보안 조건**이다. 문구 수정은 제품의 방어 구현이나 해소 증거가 아니다. 완료·적합 판정은 내리지 않는다. 아래의 ‘수정’은 문서 수정만 뜻한다.

근거는 기존 문서의 공식 출처와 최상위 에이전트가 추가 확인해 전달한 Android 공식 API 계약을 사용했다. 그 밖의 플랫폼별 가능성은 미확인으로 남겼다. ‘모든 UAC’, Secure Desktop 유지, 스마트폰 인증만의 승인 주체라는 사용자 요구를 이 감사에서 축소하거나 Windows 보호 기능 약화를 대안으로 삼지 않았다.

## 발견, 문서 수정, 남은 조건

### SR-01 · 높음 · 상승 권한만으로 매번 새 UAC를 보장할 수 있다고 읽힐 여지

- 발견: 초기 불변조건은 QR 재발급이 ‘상승된 관리 경로’를 거치도록 했지만, 이미 상승한 UI/호출자/서비스 접근 권한을 재사용하지 못하게 하는 조건이 빠져 있었다. 이는 사용자의 ‘재발급 때마다 UAC 한 번’과 동일한 계약이 아니다.
- 수정: 설치 트랜잭션의 일회성 등록과 이후 **해당 QR 발급을 위한 새 UAC 사건**을 구분했다. 발급 도전·등록 키에 결합해야 하며 `isAdmin=true`나 기존 상승 토큰을 대체 증거로 삼지 못하도록 명시했다.
- 미해결: Windows에서 새 UAC 동의 사건을 어떤 신뢰 가능한 절차로 강제·결합할지 미입증이다. 설치 중단·재시작·동시 발급·관리자 토큰 재사용을 최상위의 격리 실증 대상으로 추가했다. UAC 일반 동작 문서만으로 구현 가능성을 확정하지 않는다. [Microsoft UAC 동작 문서](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/how-it-works)

### SR-02 · 높음 · 일반 데스크톱 QR 비밀 노출과 승인키 등록 선점

- 발견: QR의 짧은 수명·일회용성만으로는 일반 사용자 Tauri 화면/IPC/메모리에서 비밀을 얻은 같은 사용자 권한의 악성 프로세스가 자기 키를 먼저 등록하는 공격을 배제하지 못한다. PC 공개키만 보여줘도 어느 폰 키를 허용할지는 별개다.
- 수정: QR 후보를 완성된 등록 프로토콜처럼 읽지 못하게 하고, 신뢰 가능한 새 관리 절차·양쪽 기기 확인·도전·PC 신원·스마트폰 키의 결합을 필수 미해결 게이트로 분리했다. 캡처 제외 플래그는 암호학적 경계가 아니며 웹뷰나 중계의 등록 성공 선언을 믿지 않도록 명시했다.
- 미해결: 사용자 승인 절차의 구체적 설계와 같은 사용자 권한 공격에 대한 방어 근거가 없다. 기존 폰의 추가 승인을 요구하는 등 UX를 바꾸는 대안은 채택하지 않았다. 등록 도중의 키 확인·취소·경쟁·재사용을 실증해야 한다.

### SR-03 · 높음 · ‘연결된 스마트폰만’의 신뢰 루트가 서명 검증보다 넓음

- 발견: 유효한 서명은 등록 공개키의 소유만 증명한다. 임의 키 등록, 사용자 쓰기 가능한 신뢰 목록, 중계/UI가 주장한 키 정책을 허용하면 스마트폰·OS 인증 요구가 무너진다.
- 수정: 최종 신뢰 목록·키 용도·폐기·요청 상태를 권한 서비스가 소유하도록 했다. 저권한 전달자의 승인/키 등록 권한을 금지하고 일반 로컬 승인 API의 부재와 내부 메시지 독립 검증을 둘 다 요구했다. 승인·거절·연결 키와 서명 도메인을 분리했다.
- 미해결: 키가 실제 승인 앱과 요청별 OS 인증 정책을 갖추었음을 인정할 근거, 하드웨어 키 증명 및 검증/폐기 정책은 미정이다. PC의 인증서/키 저장 방식과 서비스 접근 제어도 코드·실기 근거가 없다. [Android Keystore](https://developer.android.com/privacy-and-security/keystore)

### SR-04 · 높음 · 프롬프트 확인 뒤 입력하는 사이의 대상 교체

- 발견: PC/세션/요청 ID/내용 digest를 서명하고 직전에 창을 재확인해도, 그 뒤 최종 입력 전에 창·포커스·세션이 바뀌면 다른 UAC에 결정이 적용될 수 있다. HWND/PID 추가만으로 해결되는 문제가 아니다.
- 수정: 실제 Windows 요청→폰 표시→서명→세션 보조 프로세스의 최종 동작까지 결합하는 실증 게이트를 분리했다. 모호할 때 실패해야 하며 범용 입력·별도 관리자 프로세스 실행을 대안으로 연결하지 못하게 했다. 표시값의 출처와 공격자 제공 명령행/창 제목도 구별했다.
- 미해결: 실제 대상에 결합해 적용하는 Windows 경로가 아직 없다. 일반 입력 API를 선택하는 것은 이 문제의 증명이 아니다. 실증 실패는 원래 목표 미충족이며 감사관이 지원 범위를 줄여 해결할 수 없다. [SendInput 공식 API](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

### SR-05 · 높음 · Android 인증 성공과 해당 요청의 서명은 같은 보증이 아님

- 발견: OS 인증 콜백 또는 최근 잠금 해제 상태만 확인하면, 그 결과를 다른 요청/다음 서명에 재사용하는 경로가 생길 수 있다. 반대로 생체 인증만 허용하면 PIN만 설정된 정상 사용자를 잘못 거부할 수 있다.
- 수정: 공식 API 30 이상의 `timeout=0`, `AUTH_BIOMETRIC_STRONG | AUTH_DEVICE_CREDENTIAL` 구성을 후보로 명시해 이 조합을 불가능하다고 오판하지 않도록 했다. 표시한 불변 요청의 실제 `CryptoObject` 서명에 인증을 결합하고 boolean·시간창 키·무인증 키로 대체하지 못하도록 했다. `isDeviceSecure`와 현재 잠김/SIM 잠금 조건을 구분했다.
- 미해결: 선택할 AndroidX/플랫폼 인증 UI와 서명 작업의 호환성, 최소 Android 버전, PIN-only·생체·취소·프로세스 재생성·잠금 제거·키 무효화의 실기 증거는 없다. 문서상 API 가능성만으로 제품 동작을 판정하지 않는다. [KeyGenParameterSpec.Builder](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder), [KeyguardManager](https://developer.android.com/reference/android/app/KeyguardManager), [CryptoObject](https://developer.android.com/reference/android/hardware/biometrics/BiometricPrompt.CryptoObject)

### SR-06 · 높음 · 앱 정책 검사 이전 알림과 종료 상태 철회 누락

- 발견: 앱을 깨운다는 설명만으로는 비활성 시간 요청을 **표시 전에** 버린다는 계약을 보장하지 못한다. 푸시 취소·앱 타이머가 실행되지 않는 상태에선 오래된 알림이 남을 수 있다. 버린 요청의 늦은 재전송이 활성 시간에 되살아나는 경우도 명세에 없었다.
- 수정: 알림 생성 전 Android에서 종단간 인증·현재 상태·만료·일정 검사를 거치도록 하고 푸시를 신뢰되지 않는 힌트로 제한했다. 정확한 payload/수신 진입점/앱 종료 수명주기는 미정임을 드러냈다. 폐기 요청의 재등장 방지, 인증된 요청별 철회, OS 알림 만료·재진입 정리·PC 최종 만료, 오래된 알림 버튼 거부를 추가했다.
- 미해결: 절전·강제 종료·재부팅·단절에서의 전달 및 즉시 철회 보장은 실증되지 않았다. UI 철회와 PC 승인 만료 강제를 분리해 검증해야 한다. 고우선 푸시 역시 무조건 실시간 보장이 아니다. [FCM 메시지 우선순위](https://firebase.google.com/docs/cloud-messaging/android-message-priority)

### SR-07 · 중간 · 프로토콜·알림·표시 경계의 혼동

- 발견: 서명 대상의 직렬화/길이/버전/용도, 취소 신호의 인증·대상 결합, 알림 액션의 요청 귀속이 미정이면 서로 다른 의미의 메시지나 오래된 액션이 재사용될 수 있다. 공격자가 작성한 명령행은 UI와 로그에도 불신 입력이다.
- 수정: 정규화된 서명 대상 계약, 서비스 기준 만료·최종 신뢰 목록, 승인/거절 용도 분리, 취소의 PC/세션/요청/epoch 결합을 명시했다. 외부 Intent·딥링크·WebView가 임의 서명 기능이 되지 않도록 했다. 표시 원문을 HTML/실행 명령으로 해석하지 않고 비밀 포함 명령행을 기본 로그에 남기지 않도록 보강했다. 로그 보존과 입력/작업량 상한, 릴리즈 신뢰 루트도 계획에 추가했다.
- 미해결: 실제 암호 프로토콜·알림 동작 구성·입력 제한·서비스/업데이트 권한 경계는 구현되지 않았다. 무인증 거절의 잠금 화면 제3자 사용은 사용자 요구에 따른 제품 선택이며 승인 위조와 혼동하지 않는다.

### SR-08 · 중요 경계 유지 · TPM이 SYSTEM/커널 침해 후 오용까지 막지는 않음

- 발견: 초기 문서는 이 한계를 이미 구분했으며 적절하다. 다만 키 비반출만으로 신뢰 목록·실행 코드·승인 판단의 변조까지 불가능하다는 인상을 되살리면 안 된다.
- 수정: 새 QR 등록 게이트와 구현 계획에도 같은 한계를 연결했다. SYSTEM/커널 공격자에게서 일반 서비스가 절대 보호된다는 보증을 하지 않는다.
- 미해결: 사용자의 절대적 키 탈취 방지 기대와 실제 Windows/Android 신뢰 경계의 합의가 필요하다. 이 감사는 새로운 위협 모델 합의를 대신하지 않는다. [Windows의 TPM 사용](https://learn.microsoft.com/en-us/windows/security/hardware-security/tpm/how-windows-uses-the-tpm), [Android Keystore](https://developer.android.com/privacy-and-security/keystore)

## 후속 처리

이 문서 작성 당시에는 지원 범위·위협 모델 결정이 필요했으나 후속 사용자 결정으로 해당 범위가 정해졌다. QR 등록/새 UAC/정확한 프롬프트 적용의 실증은 여전히 필요하다. 이후 작성한 공통 코어의 정적 감사·수정과 최상위 실행 검증은 [현재 진행 기록](PROGRESS.md)을 따른다. 이 초기 문서 검토를 사용자 요청의 ‘작업 끝난 결과물에 대한 보안 감사’나 제품 완료로 대체하지 않는다.
