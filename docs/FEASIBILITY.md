# 구현 전 타당성 검토

검토일: 2026-09-08 · 상태: **사용자 후속 결정 반영 / 공통 코어 구현 진행**

이 문서는 구현·실기 검증 결과가 아니다. 공식 문서, 공개 소스와 사용자가 지정한 참조 저장소를 읽어 내린 설계 판단이다. 실제 UAC를 승인하거나 서비스 설치·레지스트리 변경·보호 기능 변경을 수행하지 않았다.

## 1. 먼저 결정해야 하는 지원 범위

Secure Desktop을 유지하는 원격 조작과 Windows 인증을 스마트폰 인증으로 대체하는 것은 서로 다른 문제다.

| Windows가 요구하는 것 | 스마트폰의 역할 | 현재 판단 |
| --- | --- | --- |
| 관리자 동의형 UAC의 예/아니요 | 연결된 기기의 요청별 인증·서명 후 해당 창에 동의/거절 전달 | 권한 있는 세션 보조 프로세스 경로를 검토할 수 있다. 정확한 요청 식별과 해당 창만 조작하는 실기 증거가 필요하다. 아직 구현·입증되지 않았다. |
| 표준 사용자 또는 정책상 관리자 자격 증명을 요구하는 UAC | Windows가 인정하는 관리자 인증을 추가로 제공해야 함 | Android 지문·PIN으로 만든 앱 서명만으로 기존 Windows 자격 증명을 대체하지 않는다. |
| Windows Hello 등 Windows 인증을 요구하는 권한 요청 | Windows의 인증 요구를 그대로 유지 | 별도 인증 통합 없이는 일반 동의 버튼처럼 처리할 수 없다. |
| 조직 정책상 승격 금지, 취소·만료, 식별 실패 | 승인하지 않음 | 서비스를 통한 별도 관리자 프로세스 실행으로 우회하지 않는다. |

Microsoft는 동의형과 자격 증명형 UAC를 구분한다. 기본 Secure Desktop 설정은 유지해야 한다. [UAC 동작 문서](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/how-it-works)

RustDesk가 Secure Desktop에서 UAC를 다룬다는 사용자 설명은 타당하다. 다만 RustDesk의 설명도 자격 증명이 필요한 경우 **원격 사용자가 관리자 비밀번호를 입력**하는 흐름이다. 원격 접속 인증 자체가 Windows 관리자 비밀번호를 대체한다는 근거는 아니다. [RustDesk FAQ](https://github.com/rustdesk/rustdesk/wiki/FAQ)

Windows 11 Administrator protection 역시 정책과 요청 유형을 구분해야 한다. 공식 문서는 Windows Hello 통합과 동의/자격 증명 프롬프트 정책을 설명한다. 모든 설정을 ‘항상 지문 필요’ 또는 ‘항상 예 버튼 있음’으로 단정하지 않는다. [Administrator protection](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/administrator-protection/)

Credential Provider는 자격 증명을 수집·직렬화하는 확장점이지 독자적으로 관리자 권한을 인정하는 장치가 아니다. 별도 인증 패키지 경로는 검토할 수 있으나, Windows 인증 신뢰 체계에 대한 별도 프로젝트다. 보호된 LSA에 들어가는 플러그인은 Microsoft 서명 등의 요구가 있으므로 일반 앱 코드·자체 서명만으로 배포 가능하다고 가정하지 않는다. [Credential Providers](https://learn.microsoft.com/en-us/windows/win32/secauthn/credential-providers-in-windows), [LSA 보호 요구](https://learn.microsoft.com/en-us/windows-server/security/credentials-protection-and-management/configuring-additional-lsa-protection)

**사용자가 확정한 처리 원칙:** 자격 증명형은 Windows가 요구하는 항목을 스마트폰에서 직접 입력하는 방법의 실용성과 보호 조건을 먼저 평가한다. 적절하게 처리할 수 있으면 그대로 입력할 수 있도록 구현하고, 무리가 있는 자격 증명형은 무시한다. 스마트폰의 앱 인증으로 Windows 인증을 대체하지 않는다. 어떤 자격 증명 유형을 지원/무시할지는 조사·실증 결과로 기록한다. 아직 특정 유형의 작동을 입증하지 않았다.

## 2. Rust + Tauri와 unsafe 판단

언어 선택의 잠정 결론은 **Rust + Tauri 유지**다. C++ + Electron으로 변경해도 Windows 인증 계약이나 Secure Desktop 제약은 사라지지 않는다.

| 영역 | 소유 Rust 코드의 unsafe 목표 | 격리 방법 |
| --- | --- | --- |
| 요청 상태, 인증된 메시지 처리, 일정, 저장소·보존 정책 | 0 | 크레이트 루트 `#![forbid(unsafe_code)]` |
| Tauri 명령 연결과 Android 비즈니스 로직 | 0 | 같은 금지 정책. Kotlin은 OS 인증·알림·카메라 등을 담당 |
| Windows 시스템 호출 | 제한적 필요 예상 | 독립 Windows 전용 크레이트 내부에만 FFI. 다른 모듈에 raw pointer/handle을 노출하지 않음 |
| Tauri/Win32/암호 라이브러리 내부·생성 바인딩 | 별도 집계 | 직접 작성한 unsafe와 혼합하지 않고 공급망·버전·사용 조건을 검토 |

코드가 없는 시점의 설계 예산은 전체 직접 작성 Rust 유효 코드 중 **unsafe 블록 내부 약 1–5%**, Windows 전용 어댑터 밖 **0%**다. 이는 규모에 민감한 추정이며 측정치·달성 보증이 아니다. 초기 Windows 실증 후 실제 분모, unsafe 블록 수, 내부 코드 행 수, unsafe 함수 수, 생성·종속 코드 제외 기준을 함께 보고해야 한다. 비율을 낮추려고 safe 코드나 주석을 늘리지 않는다.

예상 FFI 영역은 서비스 제어/권한 토큰, 세션·데스크톱 핸들, CNG/TPM 키, 필요한 Windows UI 접근이다. 핸들은 RAII 소유 타입으로 닫고, 스레드 귀속·버퍼 수명·실패값·길이·정수 변환 불변조건을 내부에서 검사한다. 참조는 소유자의 수명을 넘기지 않으며 데스크톱 귀속 객체를 임의로 스레드 간 이동하지 않는다. 각 unsafe에는 해당 호출의 메모리·스레드 안전성 근거가 필요하다. safe wrapper가 곧 권한 검증을 의미하지는 않는다.

사용자가 지정한 참조 저장소에서 아래 패턴을 읽었다.

- `E:\cu-best-before-Tauri\src-tauri\src\lib.rs`: `#![forbid(unsafe_code)]`, Tauri 플러그인 등록.
- `E:\cu-best-before-Tauri\src-tauri\src\media_scan.rs`: `register_android_plugin` → `PluginHandle::run_mobile_plugin` → 직렬화된 응답.
- `E:\cu-best-before-Tauri\src-tauri\gen\android\app\src\main\java\dev\dkk115\cubestbefore\MediaScanPlugin.kt`: `@TauriPlugin`, `@Command`, `@InvokeArg`, `resolve/reject`.

이는 직접 작성한 JNI 없이 통신하는 코드 사례다. 참조 앱의 성공 no-op를 승인·서명 경로에 복사하지 않는다. 비지원 플랫폼/실패는 명시적 실패여야 한다. 참조는 Activity 기반이므로 앱 프로세스 종료 후 알림 수신·철회나 인증 수명주기를 입증하지 않는다. 앱 종료 상태를 포함한 별도 백그라운드 경로가 필요하다. [Tauri 모바일 플러그인 문서](https://v2.tauri.app/develop/plugins/develop-mobile/)

## 3. 신뢰 모델: 구현하려는 방어와 보증하지 못하는 것

### 방어 대상으로 제안하는 공격자

- 공용 Wi-Fi/AP 장악, 패킷 열람·변조·재전송, 인터넷 중계 서버 장악.
- 페어링하지 않은 외부 기기, 탈퇴·폐기된 키, 다른 요청/PC의 서명 재사용.
- 관리자 권한을 얻지 못한 로컬 프로세스의 승인 위조·페어링·명령 주입.
- 잠금 화면 알림 버튼을 누르는 제3자, 인증을 취소하거나 우회하려는 앱 호출.

승인 권한은 스마트폰에서 만든 요청별 인증 요구 서명 키에만 둔다. PC가 이 서명을 대신 만들 수 없어야 한다. 거절은 별도 용도로 제한한 인증 비요구 키를 사용하고 승인으로 해석될 수 없도록 메시지 도메인과 키 용도를 분리한다. 양쪽의 연결·암호화 키와 승인 키도 분리한다. 다만 서명 검증만으로 ‘등록된 키가 실제 스마트폰의 인증 요구 키’라는 사실까지 증명되지는 않는다. 최초 등록의 권한과 키의 인증 정책을 확인하는 절차도 같은 신뢰 경계에 속한다.

신뢰 목록·키 용도·기기 폐기 상태·요청 상태의 최종 판단은 권한 있는 서비스가 소유한다. 일반 사용자 쓰기 가능한 설정 파일, Tauri IPC 입력, 중계 응답, 푸시 토큰 또는 앱의 `authenticated=true` 값으로 이 상태를 바꾸지 못하게 한다. 저권한 통신 프로세스는 전달자일 뿐 승인자나 키 등록자가 아니다. 로컬 공개 인터페이스에 승인 명령을 만들지 않는 것과, 내부 전달 메시지의 서명을 권한 서비스가 직접 검증하는 것은 둘 다 필요하다.

Windows는 TPM-backed CNG 비반출 키와 서비스 SID 전용 접근 제어를 우선 검토한다. TPM은 키 원문을 일반 메모리로 내보내지 않는 보호를 제공할 수 있다. **키 추출 방지와 키의 허가되지 않은 사용 방지는 별개이므로 둘 다 설계한다.** 사용자는 이미 SYSTEM/커널이 침해된 경우를 위협 모델에서 명시적으로 제외했다. 이는 미결정 사항이나 작업 중단 사유가 아니다. 정상 OS 아래의 일반 권한 로컬 악성코드와 네트워크 공격자를 방어한다. [Windows TPM 설명](https://learn.microsoft.com/en-us/windows/security/hardware-security/tpm/how-windows-uses-the-tpm)

Android도 하드웨어 Keystore와 키 사용 시 인증을 검토한다. 공식 문서 역시 프로세스/OS 침해 시 키 원문 추출과 해당 기기 내 키 사용을 구분한다. `isDeviceSecure`로 PIN/패턴/비밀번호 존재를 판정해야 하며, ‘현재 화면이 잠겨 있음’을 잠금 설정 유무로 오인하지 않는다. SIM 잠금까지 포함할 수 있는 `isKeyguardSecure`를 이 조건의 대체값으로 쓰지 않는다. 승인 키는 인증 콜백의 boolean이 아닌 실제 암호 작업에 결합해야 한다. [Android Keystore](https://developer.android.com/privacy-and-security/keystore), [KeyguardManager](https://developer.android.com/reference/android/app/KeyguardManager), [BiometricPrompt CryptoObject](https://developer.android.com/reference/android/hardware/biometrics/BiometricPrompt.CryptoObject)

**확정한 범위:** 이미 SYSTEM/커널이 침해된 경우는 사용자 결정에 따라 범위 밖이다. 일반 권한 악성코드가 이 서비스를 통해 상승하는 공격은 범위 안이다. TPM/하드웨어 키가 없는 기기에서 조용히 소프트웨어 키로 바꾸지 않으며 지원·거부 정책은 별도로 정한다.

## 4. 보안 설계 초안의 필수 불변조건

아래 항목은 구현된 기능이 아니라 후속 설계·테스트 계약이다.

1. QR은 PC 신원 키와 짧은 수명의 일회용 페어링 비밀/도전을 결합하는 후보 경로다. 키 확인과 암호 프로토콜의 정확한 선택은 별도 명세로 고정한다. TLS만 믿거나 최초 접속 상대를 그대로 신뢰하지 않는다. QR 원문은 로그·분석·중계 서버에 남기지 않는다. **QR을 띄운 사실이나 PC 공개키를 읽은 사실만으로 어느 스마트폰 키의 등록을 허용할지 결정되지는 않는다.** 이 등록 권한 문제는 아래 4.1의 미해결 실증 게이트다.
2. 설치 직후 최초 등록 권한은 설치 트랜잭션에 결합된 일회성 권한이다. 실패·시간 초과·재시작으로 열린 등록 모드가 남지 않아야 한다. 이후 QR 발급에는 사용자가 요구한 **그 발급을 위한 새 UAC 승인**이 필요하다. 기존 상승 토큰, 오래 살아 있는 관리자 UI, 서비스에 접근 가능한 관리자라는 사실만으로 이 조건을 충족했다고 기록하지 않는다. UI가 보낸 `isAdmin=true` 같은 값도 권한 증명이 아니다. 새 UAC 사건을 등록 도전과 결합하는 Windows 경로는 아직 입증되지 않았다.
3. 인터넷 연결·중계는 저권한 Rust 프로세스에 둔다. LocalSystem 보조 프로세스에 인터넷 파서나 WebView를 넣지 않는다. 중계가 훼손되어도 내용·승인을 위조할 수 없는 종단간 인증·암호화를 적용한다. 중계의 연결 메타데이터 관찰과 서비스 거부까지 없어진다고 주장하지 않는다.
4. 로컬 관리 경로에는 승인·임의 실행·일반 키보드/마우스·임의 파일 쓰기 명령이 없다. 내부 전달이 필요하더라도 페어링 기기 서명 없는 승인 결정을 받아들이지 않는다. 서비스 권한 경로에서 서명·기기 폐기·요청 결합·재전송 방지를 독립적으로 강제한다.
5. 요청은 PC 신원, 사용자 세션, 요청 ID, 재시작 epoch, 난수, 요청 내용 digest, 만료, 결정 종류에 결합한다. 플랫폼에서 식별한 실제 요청만 등록하며 UI/중계가 임의 내용을 원본으로 주장할 수 없다. 직렬화·길이 상한·버전·서명 도메인·허용 알고리즘을 고정해 같은 바이트가 다른 의미로 해석되지 않게 한다. 같은 요청은 원자적으로 한 번만 소비한다. 서비스는 자신의 만료 기준과 현재 신뢰 목록을 최종 적용하며 폰·중계의 시각이나 ‘이미 검증함’ 주장으로 이를 연장·대체하지 않는다.
6. 창이 사라지거나 바뀐 뒤 도착한 승인은 버린다. HWND/PID 재사용, 사용자 전환, 서비스 재시작, 여러 기기 응답, 만료/승인 동시 도착을 다룬다. 서명 직후의 검사만으로 TOCTOU가 해결됐다고 주장하지 않는다.
7. blind `Enter`, 좌표 클릭, 임의 창 입력을 승인 구현으로 출하하지 않는다. Windows가 표시한 특정 요청과 실행할 동작을 결합할 수 있는지 실증하고, 결합이 불명확하면 동작하지 않는다. `SendInput`은 범용 입력 수단이지 요청에 결합된 UAC 승인 API가 아니다. [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)
8. 앱 이름·명령행·발행자를 못 읽으면 지어내지 않는다. 터미널의 기본 화면은 셸 이름과 실행 파일, ‘더 보기’에서 가능한 실제 명령을 보여준다. 공격자가 만든 창 제목·파일 설명·명령행을 Windows가 보증한 발행자 정보로 승격하지 않는다. 표시한 원본과 서명 대상은 같은 불변 요청이어야 한다. 원문은 HTML이나 실행 가능한 Tauri 명령으로 해석하지 않고, 눈속임이 가능한 제어문자·긴 내용의 표시 규칙도 정한다. 요청 내용을 무결성 검증 없이 신뢰하거나 로그에 비밀이 포함된 명령행을 기본 저장하지 않는다. 앱 이름·경로·서명 확인이 실행 후 프로그램의 모든 행동을 보증하지는 않는다.
9. 잠금 없는 스마트폰에서는 작동하지 않는다. 잠금이 있는 폰에는 불필요한 잠금 설정 요청을 띄우지 않는다. 승인에만 인증을 요구하고 거절 키로 승인을 만들 수 없게 한다. 승인 버튼은 임의 바이트 서명 기능이 아니라 인증된 현재 요청 한 건에 대한 네이티브 인증·서명 경로에만 연결한다. 알림·딥링크·외부 Intent·WebView 입력으로 인증을 생략하거나 요청을 바꿀 수 없어야 한다.
10. 서명 검증을 통과해도 Windows에서 실제 반영되기 전에는 ‘승인됨’으로 표시하지 않는다. 전송·수신·Windows 적용·취소·만료·실패 상태를 구분한다.

### 4.1 QR 등록과 매번 새 UAC: 아직 풀리지 않은 부트스트랩

일반 사용자 데스크톱의 Tauri 화면·IPC·프로세스 메모리에 등록용 비밀이 나타나면 같은 사용자 권한의 악성코드가 이를 얻어 자기 키를 먼저 등록하려는 경쟁을 할 수 있다는 설계 위험이 있다. QR을 짧게 표시하거나 캡처 제외 플래그를 켠 것을 암호학적 접근 제어로 취급하지 않는다. 공개키만 QR에 넣어 비밀 노출을 없애도 **새 스마트폰 키를 승인할 권한**은 따로 해결해야 한다.

따라서 새로 승인받은 신뢰 가능한 관리 절차, 양쪽 기기 확인, 일회용 도전, 허용할 스마트폰 키와 PC 신원, 설치/등록 트랜잭션을 어떻게 한 번의 등록으로 결합할지 별도 명세·실증이 필요하다. 키 확인이 끝나기 전에 등록하거나, 중계가 알려준 첫 번째 키를 채택하거나, 웹뷰가 등록 성공을 선언하게 해서는 안 된다. 이미 상승한 호출자·여러 QR 발급 경쟁·발급 취소·설치 중단·권한 재사용을 포함한다. Windows UAC 동작 문서만 읽은 것으로 ‘매번 새 UAC를 강제할 수 있다’고 확정하지 않는다. [UAC 동작 문서](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/how-it-works)

이는 **미해결인 설계 조건**이다. 기존 스마트폰의 추가 동의처럼 사용자 절차를 바꾸는 선택지를 독자적으로 채택하지 않는다. 여기서 다루는 공격자는 정상 OS의 일반 권한 로컬 프로세스이며, 이미 SYSTEM/커널이 침해된 경우는 제외한다.

### 4.2 Android의 요청마다 인증: API 가능성과 제품 입증을 분리

공식 API에는 API 30 이상에서 `setUserAuthenticationParameters`의 `timeout=0`으로 매 키 사용 인증을 요구하고, `AUTH_BIOMETRIC_STRONG | AUTH_DEVICE_CREDENTIAL`을 지정하는 구성이 있다. 그러므로 PIN/패턴/비밀번호와 매 사용 인증의 조합 자체가 불가능하다고 판단하지 않는다. 다만 이 API 계약이 선택한 AndroidX/플랫폼 인증 UI, 서명용 `CryptoObject`, 기기별 하드웨어 키 구현에서 끝까지 동작한다는 실기 증거는 아직 없다. [KeyGenParameterSpec.Builder](https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder)

인증은 표시한 불변 요청의 서명 작업과 결합한다. 단순 인증 성공 콜백, 최근 잠금 해제 여부, 긴 인증 유효 시간창을 대체 증거로 삼지 않는다. PIN만 설정된 기기·생체 인증 등록 기기·인증 취소·다른 요청 도착·프로세스 재생성·잠금 해제 수단 제거·키 무효화를 각각 다뤄야 한다. 지원되지 않는 경로를 발견했을 때 생체 인증만 강제하거나 인증 없는 키로 조용히 바꾸는 것은 요구사항 충족이 아니다.

PC가 등록 키의 하드웨어 보관·인증 정책을 어떤 증거로 인정할지, 키 증명을 쓴다면 도전·체인·정책·폐기 및 지원 기기를 어떻게 다룰지도 미정이다. 앱이 보고한 설정이나 키 소유 증명만으로 매번 OS 인증을 받는다는 보증은 만들 수 없다. 이 조건과 최소 Android 버전을 정하지 않은 상태에서 ‘연결된 승인기만 승인할 수 있다’고 완료 판정하지 않는다.

### 4.3 실제 UAC 요청에 적용하는 마지막 단계

스마트폰 서명은 요청 데이터에 대한 결정이지 특정 Windows 프롬프트에 적용됐다는 증거가 아니다. 서명 검사 후 창·포커스·세션을 다시 확인하고 입력하는 순서에도 그 사이 대상이 바뀔 수 있다. HWND/PID와 명령행 digest를 추가하는 것만으로 이 틈이 닫혔다고 주장하지 않는다.

Windows가 소유한 실제 요청, 폰에 보여준 정보, 최종 수행 동작의 결합을 세션 보조 프로세스까지 유지할 수 있는지 입증해야 한다. 여러 요청·다른 사용자·재시작·프롬프트 교체 때도 적용이 불명확하면 실패해야 한다. 이 실패 원칙은 ‘모든 UAC’ 요구를 줄이기로 합의했다는 뜻이 아니며, 실증 실패 시 원래 목표의 미충족으로 보고한다. 이 게이트를 통과하기 전에 일반 입력 에뮬레이션을 제품 승인 경로에 붙이지 않는다.

## 5. 지연·알림에 관한 현실적 계약

0초는 목표이지 보증할 수 있는 지연 값이 아니다. 연결이 살아 있을 때와 Android 절전/프로세스 종료 상태를 분리해 측정한다. 예비 목표는 연결 유지 상태에서 요청 발생→알림 표시 p50 250ms, p95 750ms 이내로 두되 **미측정 목표**로만 취급한다. 지역·통신사·전파 상태·폰 절전 상태를 기록한다. 네트워크 단절·강제 종료까지 동시 표시한다고 주장하지 않는다.

백그라운드 깨우기에 FCM을 채택할 경우 별도 프로젝트·자격 증명·중계 배포가 필요하다. 아직 어떤 외부 계정도 만들거나 비용을 발생시키지 않았다. 고우선 메시지는 사용자에게 보이는 시급한 알림을 위한 기능이며, 계속 표시하지 않으면 우선순위가 낮아질 수 있다. [FCM 메시지 우선순위](https://firebase.google.com/docs/cloud-messaging/android-message-priority)

푸시는 신뢰되지 않는 깨우기/전달 힌트이지 PC 신원·승인·취소의 근거가 아니다. 알림 생성 전 Android가 종단간 인증, 현재 요청 상태, 만료, 사용자 일정을 검사해야 한다. 이 검사 없이 OS가 먼저 알림을 표시하는 경로는 요구에 맞지 않는다. FCM의 정확한 payload 종류, 앱 종료 상태의 수신 진입점, Kotlin에서 Rust 정책을 호출하는 수명주기는 아직 선정·실증하지 않았다. 요청 본문·명령행·페어링 비밀을 푸시 알림 원문에 노출하지 않는다.

스마트폰의 요일/시간대 정책이 최종 권한을 가진다. 미설정이면 항상 알림을 허용한다. 허용 시간 밖에는 요청을 큐나 과거 요청 목록에 보관하거나 나중에 표시하지 않고 즉시 버린다. PC가 알고 있는 일정으로 불필요한 푸시를 줄이더라도 Android의 수신 시 재검사는 생략하지 않는다. 시간 밖에 버린 요청이 지연된 푸시·전송 재시도·재접속 때문에 이후 되살아나지 않도록 전달 상태와 재전송 규칙도 정해야 한다. 자정을 넘는 일정·시간대 변경·중복 메시지를 명세와 테스트에 포함한다.

PC의 취소/만료 신호로 알림을 철회한다. 철회 신호는 PC 신원·세션·요청·epoch에 인증·결합해 다른 요청의 알림을 없애지 못하게 한다. 철회 신호가 지연·유실될 수 있으므로 폰도 만료 시점에 자체 철회하고 재접속 시 상태를 조정해야 한다. Android의 절전·강제 종료 상태에서 앱 타이머나 푸시 처리의 정확한 실행을 보장했다고 표현하지 않는다. OS 알림 만료 기능, 재진입 시 정리, PC 최종 만료 검사를 함께 설계하며, 오래된 알림 버튼으로는 승인 작업을 시작하지 못하게 한다. 즉시 철회 UI와 승인 만료 강제는 별도 검증 대상이다.

알림 동작은 요청별 식별자에 결합하고 외부 앱 호출·이전 알림 액션 재사용으로 요청을 바꾸거나 인증을 건너뛰지 못하게 한다. 허용한 무인증 거절은 잠금 화면에서도 제3자가 거절할 수 있는 제품 선택이지만, 거절 키나 경로로 승인을 만들 수 있어서는 안 된다. 시간 밖 폐기 요청에는 사용자 이력/알림을 만들지 않는다. 허용 시간에 수신한 요청의 만료만 기록으로 남긴다. 서버 시간 불일치가 승인 수명을 연장하지 않도록 단조 시계와 보수적 만료 판단을 설계한다.

## 6. 다음 작업을 시작할 조건

사용자의 자격 증명형 처리와 위협 모델 결정이 반영되었다. 공통 코어·CI는 진행하며, Windows 경로는 격리된 테스트 환경에서 정확한 요청 식별·대상 결합과 스마트폰 자격 증명 입력을 실증한다. 그 전에는 범용 입력이나 별도 관리자 프로세스 실행을 대신 연결하지 않는다.

이후 요청 검증 코어, Android 네이티브 기능, Tauri 화면, 네트워크 중계, 서비스 설치/관리, CI/릴리즈를 순차·병렬 구현한다. 하위 에이전트는 코드 작성·정적 검토만 수행하고 실행 검증은 최상위 에이전트가 전담한다. 구현 후 보안 감사·수정과 새 아키텍처 리팩터링 에이전트를 거친다.

완료를 주장하려면 실기 증거가 필요하다. 참고 문서를 읽은 것, UI 목업, 단위 테스트, 컴파일 성공을 실제 원격 UAC 승인 성공으로 바꿔 적지 않는다.
