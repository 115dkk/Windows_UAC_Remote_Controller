# 현재 구현과 검증

2026-09-11 · **개발 진행 중. 원격 UAC 승인기 전체가 완성된 상태는 아니다.**

## 9월 11일 밤: 등록 절차 양쪽 구현과 실험실 증거

- 서비스 쪽 프롬프트 감시 세션, 중계 주소 설정 파일과 CLI 동사, 기기별 경로를 담는 신뢰 장부 2판,
  휴대폰 쪽 등록 절차(중계 접속, 고정 TLS, 여섯 자리 비교, 확인, 서명된 수락, 저장)와 상시 접속
  다이얼러, 그리고 스캐너 화면에서 절차를 이끄는 Kotlin 배선을 검증해 올렸다. 워커 코드는 그대로
  통과하지 않았다. QR에서 이어받은 시계가 네이티브 콜백 안에서 관측을 거부해 키 생성이 항상 실패하던
  결함은 제품 경로의 문제여서 고쳤고, 나머지는 테스트 픽스처의 잘못이었다.
- 실험실 러너에서 서비스가 키를 저장하지 못하는 원인을 확인했다. 쓰기 제한 서비스 토큰으로는
  `NCryptFinalizeKey`가 접근 거부(`0x80090010`)로 끝나고, 같은 실행 파일을 무제한 서비스 SID로
  다시 시작하면 키가 만들어진다. 그래서 ADR 0028로 서비스 SID 유형을 무제한으로 바꿨다. 개발 PC의
  `0x80090030`도 같은 부류일 가능성이 크지만, 그 PC에서는 아직 다시 시험하지 않았다.
- 무제한 SID로 키를 만든 뒤에는 소프트웨어 키 공급자가 키 보안 설명자의 접근 마스크를 파일 권한 형태로
  바꿔 돌려주는 탓에 정책 검사가 거부했다. 실험실 빌드가 남긴 실제 설명자를 보고, 두 고정 주체에 한해
  일반 형태와 공급자 변환 형태의 전체 권한을 모두 받도록 정책을 고쳤다. 실험실 표식이 있는 실행 파일은
  패키징 단계에서 거부한다.
- 그 결과 실험실 러너에서 서비스가 처음으로 실행 상태에 도달했다. 키가 만들어지고 신뢰 장부와 활동 기록이
  써졌으며 프롬프트 관측 요청도 접수됐다. 다만 헬퍼 감독자가 아직 쓰기 제한 토큰을 요구해 거부했고(고쳤다),
  예약 작업으로 띄운 관리자 권한 요청은 15초 안에 consent.exe를 만들지 않았다. 다음 실행에서 40초 동안의
  프로세스 변화와 작업 상태를 기록해 원인을 본다.
- APK 서명용 키스토어를 만들어 저장소 시크릿으로 넣었다. 다음 판부터 같은 키로 서명된다.
- PC 쪽 등록 절차도 들어갔다. 보호된 파일의 중계 주소와 새 경로로 초대를 만들고, 중계를 거쳐 휴대폰의
  제출을 받아 Android 증명을 검증하고, 서로 고정한 TLS 위에서 후보를 서명해 보낸 뒤 렌더러에 여섯 자리를
  띄우고, 양쪽 확인 뒤 장부에 기록하고 수락을 서명해 보낸다. 준비가 끝난 뒤에는 등록된 기기마다 중계 연결
  하나를 유지하는 다이얼러가 돈다. 서비스 크레이트의 호스트 테스트 234개가 통과한다.
- 실험실에서는 헬퍼 감독자의 토큰 검사 하나가 아직 걸렸고(길이가 다른 응답을 플래그로 읽도록 고쳤다),
  러너의 관리자 계정에는 필터링된 토큰이 없어 관리자 권한 요청이 창 없이 통과했다. 다음 실행은 러너에
  표준 사용자를 만들어 그 사용자로 요청한다.
- 실험실 러너에 표준 사용자를 만들어 그 계정으로 관리자 권한을 요청하자 실제 consent.exe가 대화형 세션에
  나타났다. 서비스는 그동안 실행 상태였다. 프롬프트 관측 헬퍼는 그다음 단계인 토큰 세션 변경에서 접근 거부를
  받았는데, SeTcb 권한은 켜져 있었고 다시 켜도 달라지지 않았다. SYSTEM 예약 작업으로 같은 호출을 재현해 보니
  서비스가 요청하는 명시적 토큰 권한 조합으로 복제한 토큰은 세션 변경이 거부되고, MAXIMUM_ALLOWED나 전체
  권한으로 복제하면 성공한다. 빠진 권한 비트 하나를 찾는 실험이 다음 실행에 들어 있다.
- 휴대폰 QR 스캐너 버튼을 눌러도 아무 일이 없던 원인을 찾았다. Tauri 권한 목록에 등록된 명령 열한 개 중
  아홉 개만 허용돼 있었고, 스캐너 열기와 요청 상세 읽기 두 명령이 빠져 있어 호출이 IPC 경계에서 거부됐다.
  두 권한을 넣고, 핸들러의 명령과 권한 목록이 어긋나면 품질 게이트가 잡도록 검사를 추가했다. 그 뒤 수명주기
  검사가 원래 단계와 첫 잠금 해제, 스캐너 두 사례(화면 버튼으로 연 보호 다이얼로그와 배경 전환 시 취소, QR 없는
  화면 68장)까지 모두 통과했다. 이 시점(2049da8)에 품질·수명주기·패키지·갤러리 검사가 전부 초록이다.
- 이 시점에 남아 있던 일(W9, W10, CI 통과, 실험실의 세션 변경)은 다음 절에 이어서 적었다.

## 9월 11일 저녁: Claude 인수 뒤 첫 정리

Codex가 `6da41e0`에서 멈춘 뒤 Claude가 이어받았다. 먼저 드라이브가 다시 가득 차지 않도록
빌드·다운로드 명령을 여유 공간 기준으로 거부하는 훅과 이 저장소 전용 target 경로 설정을 넣었다.

- `6da41e0` 품질 실행의 실패 원인이던 ABI 9 단정과, 재부팅 뒤 WebView 준비를 2초 안에 요구하던
  계측 코드를 고쳤다. 그 뒤 에뮬레이터 수명주기 전체와 첫 잠금 해제가 다시 통과했다.
- 새로 도는 QR 스캐너 검사는 아직 실패한다. 다이얼로그가 30초 안에 열리지 않는데, 사후 덤프에는
  앱 창이 없어 원인을 알 수 없었다. 열기 경로에 고정 문구 진단을 넣어 다음 실행에서 확인한다.
- ADR 0027로 프리릴리즈 설계를 정했다. 중계 서버를 거치는 등록 절차, 보호된 화면의 QR과 여섯 자리
  비교, 서비스가 직접 중계에 접속하는 방식, 실험실용 소프트웨어 키 공급자 빌드 옵션이다.
- 프로토콜 코덱, 렌더러 화면, 프롬프트 감시 헬퍼, Windows 관리 앱의 연결 진입점, 휴대폰 화면 상태를
  구현해 로컬 검사(fmt, 테스트, Clippy)를 통과시키고 `a48b14e`까지 올렸다. 실제 UAC 창에 적용한
  기록은 아직 없다. 태그를 붙이면 설치 파일과 APK를 프리릴리즈로 올리는 워크플로도 추가했다.
- 호스팅 Windows 러너에는 TPM이 없어 개발 PC의 서비스와 같은 `0x80090030`이 난다. 그래서 일회용
  러너에서만 쓰는 실험실 빌드로 서비스 시작과 실제 consent.exe 관측을 시험하는 워크플로를 만들었다.
  개발 PC에서는 새 UAC·TPM 실험을 하지 않았다.

## 9월 10일 저녁: 실제 시작 오류와 검증 진행

`7b9df1f`의 Windows·Linux Rust 품질 검사와 Android 코어·APK·Windows 설치
파일 검사는 통과했다. 전체 품질 실행은 통신 보안 모델의 미완료 항목으로
실패한 상태다. Windows 요청을 휴대폰에서 실제로 승인한 결과는 아직 없다.

사용자가 승인한 설치 실험에서 TPM 암호화 공급자를 여는 첫 호출이
`0x80090030`으로 실패했다. 일반 사용자 실행에서는 같은 공급자 열기가
성공했다. Windows에 실행 상태를 알린 뒤 초기화하도록 순서를 바꾼 별도
시험판도 같은 오류를 냈다. 따라서 시작 순서만 바꿔서는 해결되지 않았다.
TPM 초기화, 키 삭제, 프로그램의 권한 제한 완화나 백신 설정 변경은 하지 않았다.
Daybreak Blue의 검토로 별도 진단 방법을 좁혔으며, 사용자가 일회성 SYSTEM
진단을 허락해 준비 중이다. 실제 실행과 결과 확인은 다음 단계다.

첫 화면의 목적 설명과 제품 중심 문구는 수정했고, 실제 CI 갤러리의 원본
화면을 [이슈](https://github.com/115dkk/Windows_UAC_Remote_Controller/issues/1#issuecomment-5616495027)에 올렸다.
안드로이드 알림 렌더러도 확인했지만, 부팅·실제 휴대폰 인증을 검증한 것으로
취급하지 않는다.

연결 해제 이후 승인 차단 속성은 보조 명제 네 개와 함께 실제 Tamarin
실험에서 증명됐다. 이 결과를 정식 검사에 연결하고 있으며, 정상 승인 사례와
고장 난 모델의 공격 사례까지 모두 통과해야 전체 검증을 완료한다.
QR 최초 등록, Windows 실제 요청 처리, 자격 증명형 처리의 실증, 최종 감사와
리팩터링은 여전히 남아 있다. 프리릴리즈 공개와 C·E 드라이브 정리도 하지 않았다.

아래는 각 구현 단계 당시의 기록이다. 최신 상태와 재사용할 구성요소는
[개발 상태](DEVELOPMENT_STATUS.md)를 기준으로 확인한다.

## 9월 10일: 요청 수신·알림·응답 연결부 추가

ABI8에서 실제 소켓과 같은 Rust 저장소를 연결하고, 검증된 요청의 표시,
승인·거부 전송, PC 종료 통지의 기록 반영을 묶었다. 원래 만료 시간은
유지하며, 시각 동기화를 갱신해도 기존 요청의 시간이 늘어나지 않는다.
설정 전용 시작 제한은 전체 복구·알림 정리·결과 반영 경로로 교체했다.
QR 등록과 연결할 주소를 준비하는 절차, 실제 Windows 요청 생산자는 아직 없다.

ROOT가 Rust 연결부 테스트 57개, 화면 테스트 47개, 화면용 데이터 테스트
46개, Tauri 호스트 단위 테스트 23개를 통과시켰다. 관련 6개 크레이트의
Clippy `-D warnings`도 통과했다. 휴대폰 테스트에는 시험용 키와 실제
TCP/TLS 소켓을 사용했으며, 실제 Android 인증·원격 UAC 성공을 뜻하지 않는다.
로컬 DLL 링크에서는 기존 한국어 MSVC 진행 문구 경고가 발생했다.

로컬 TCP 종료 검사는 아직 실패한다. 앱·TLS 코드가 없는 Tokio 대조군과
별도 .NET 대조군에서도 전송 후 조기 EOF가 발생했다. 운영체제나 보안 설정은
변경하지 않았고, 엄격한 수신 검사를 유지해 CI의 Windows/Linux에서 확인한다.
전체 검사가 통과했다고 기록하지 않는다.

Kotlin 알림·동작·시계 연결과 순수 테스트 23개는 작성했으며 새 APK 검사는
대기 중이다. 새 Chromium 갤러리 44개 사례와 실제 알림 코드를 공유하는
별도 Android 테스트 앱도 CI 실행 전이다. 별도 앱에는 키·인증·서비스·통신
기능이 없으므로 그 화면을 실제 제품의 인증 성공으로 표시하지 않는다.
새 화면은 아직 이슈에 게시하지 않았다.

정적 검토에서 찾은 대기 기한·스레드 오류·정리 재시도·알림 교체 세대·시각
변경 경로를 수정했다. 전체 제품의 최종 보안 감사와 별도 최종 구조 리팩터링은
아직 남아 있다. 요청 보안 모델의 시간 초과, 실제 기기 검증, PR/main 릴리스,
작업 종료 후 C/E 정리도 미완료다. [결정 기록](adr/0015-native-intake-and-request-presentation.md).

## 9월 10일: 휴대폰 거부 동작 연결 중

[`ce69210` 품질 실행](https://github.com/115dkk/Windows_UAC_Remote_Controller/actions/runs/34368756647)의
Windows·Linux·Android 코어 작업과
[같은 커밋의 APK 실행](https://github.com/115dkk/Windows_UAC_Remote_Controller/actions/runs/34368756768)이
통과했다. 전체 품질 실행은 요청 보안 모델의 시간 초과로 실패했다. 해당
모델에서 요청별 인증 결합과 처음 열린 요청의 결합은 증명됐지만, 나머지
7개 요청 항목과 2개 공격 검사는 시간 초과였다. 연결 모델의 4개 항목과
키 검사 제거 공격은 통과했다. 아래 항목별 테스트 수치는 각 단계의 기록이지 현재 전체
제품의 완료 여부를 뜻하지 않는다.

현재는 거부 작업이 같은 요청의 진행 중 승인·준비된 서명·부분 전송을
취소하고, 휴대폰의 실제 인증 작업이 끝났는지 확인한 뒤 거부용 키를 쓰도록
Rust와 Kotlin의 연결부를 구현 중이다. 해당 요청의 인증 작업이 취소됐어도
명시적으로 정리되기 전에는 Rust의 작업 자리가 남아 있음을 확인하는
조회 함수를 추가했다. ROOT가 관련 Rust 테스트 19개와 Clippy를 실행해 통과했다.
휴대폰의 실제 키 사용·알림 버튼·요청 수신·전송 연결은 아직 검증하지 않았다.
설정 전용 Application 시작 조건은 유지하며 가짜 요청으로 이를 활성화하지 않는다.

후속 Rust 연결부 검사에서는 새 사례 17개를 포함한 단위 테스트 40개와
실제 전송 테스트 6개가 통과했다. 앱에 결과를 돌려주기 직전의 취소·만료,

### 부팅 시 시작과 연결 보안 CI

Android에는 기본 활성화된 부팅 수신기와 실제 포그라운드 서비스가 있다.
부팅 후 첫 잠금 해제 전에는 저장된 요청·키를 열지 않으며 인증 화면도
띄우지 않는다. 앱에서 서비스를 끄면 자동 시작도 끄고, 다시 시작하면
자동 시작을 켠다. 서비스 상태와 알림 설정을 따로 읽으므로 서비스가
꺼졌을 때도 다시 시작하는 화면을 표시한다. APK 선언·Kotlin 수명주기
테스트·Rust 연결부·화면 CI를 검사했지만 **실제 휴대폰 재부팅 시험은 남았다.**

CI는 고정된 Tamarin 1.12.0과 Maude 3.5.1을 실행한다. 연결 상대의 키 검증,
기밀성, 요청 결합·일회성 처리·등록 해제·취소·만료를 검사하며, 보호 장치를
제거한 모델에서 실제 공격 예제가 나오는지도 요구한다. 요청 모델의 증명
시간 초과가 남아 내부 상태 표현과 탐색 순서를 수정했고,
[`795dd9b` 실행](https://github.com/115dkk/Windows_UAC_Remote_Controller/actions/runs/34353029001)은
전체 실패로 끝났다. 연결 모델 4항목과 키 검사 제거 공격, 요청별 인증 결합
1항목은 완료했지만, 나머지 요청 8항목과 요청 공격 2개는 시간 초과였다.
필수 보조정리와 공격 검사는 줄이지 않았으며 별도 부분 증명 진단을 준비한다. 상징적 모델은
실제 키 보관·휴대폰 인증·Windows 동작이나 구현 전체를 증명하지 않는다.

### 저장 공간

실험에 앞서 사용자가 추가로 허가한 공간 확보 범위에서, 이 작업 전용
Rust 증분 빌드 캐시만 정리했다. C:의 실제 여유 공간은 약 **3.31GB 증가**했다.
소스·Git·키·설치물·검증 자료는 보존했고 E: 파일은 삭제하지 않았다.
이후 빌드는 증분 캐시를 끄고 가능한 작업을 CI로 옮겼다. 전체 구현·최종
리팩터링·검증 후에 하기로 한 C·E 드라이브 정리는 아직 수행하지 않았다.

### 후속 소스 검사: 요청 복구 전 휴대폰 키 확인

기존 단일 수신함 소유자에 전체 요청 복구용 키 사전 확인 경로를 추가했다.
저장소 잠금을 유지하고 복구 결과를 확정하기 전에 기존 키를 확인할 수 있다.
실패나 중단은 새 설치로 덮어쓰지 않으며, 기존 설정 전용 시작 조건도
바꾸지 않았다. ROOT의 Windows 호스트 테스트 123개와 fmt·Clippy가 통과했고
이 중 새 테스트 9개가 잠금·복구 순서·손상·실패·내구성 경계를 검사한다.
이는 향후 요청 수신 연결을 위한 준비이며 실제 휴대폰 알림·키 검증이나
Application의 수신 기능을 켠 결과는 아니다. 이 후속 변경의 별도 CI도 필요하다.

### 후속 구현: 요청에 묶인 거부 서명

기존 수신함의 원래 요청·등록 세대·기기·만료 기한에 묶인 일회성 거부
작업을 추가했다. 승인용 키나 승인 문구로 만든 서명은 거절하고, 거부용
키가 서명한 정확한 거부 문구만 받아들인다. 이 경로에는 별도 인증 단계가
없으며 로컬 서명만으로 Windows에서 거부됐다는 기록을 만들지 않는다.
취소·등록 해제·앱 소유자 종료는 준비된 결과도 무효화한다.

ROOT가 새 테스트 17개를 포함한 해당 크레이트의 140개 호스트 테스트와
fmt·Clippy를 실행해 통과했다. 실제 Android 키 사용, 같은 요청의 진행 중
승인 취소, 거부 버튼과 전송 연결은 아직 구현해야 한다. 새 소스의
플랫폼 CI와 실제 휴대폰 검증을 이 호스트 결과로 대신하지 않는다.

이후 거부 결과를 실제 암호화 소켓에 넘기는 타입별 전송 경로도 추가했다.
기존 승인 검사를 함께 사용하며 원래 취소 상태·요청·만료 기한을 부분
전송까지 유지한다. 새 통합 테스트 10개를 포함한 150개 호스트 테스트와
fmt·Clippy가 통과했다. 17바이트 단위의 실제 전송 도중 취소·기기 재등록·
알림 시간 변경·만료가 발생하면 남은 전송을 중단하는 경우를 검사했다.
로컬 소켓에 썼다는 사실은 PC가 받았거나 Windows가 거부했다는 뜻이 아니다.
Android 키·버튼·백그라운드 연결 소유자에 이 경로를 연결하는 일은 남아 있다.

요청별 승인 취소도 추가했다. 인증 작업이 끝나더라도 아직 준비된 서명이나
부분 전송이 남아 있으면, 같은 PC·서비스 실행 구간·요청의 승인만 취소한다.
살아 있는 문맥은 최대 64개까지 유지하고 실제 마지막 참조가 사라진 항목만
비운다. 새 8개 사례를 포함한 158개 호스트 테스트와 fmt·Clippy가 통과했다.
이 취소는 실제 인증 창·키 작업 종료나 이미 전송된 바이트의 회수를 뜻하지
않는다. 거부 처리 동안 같은 요청의 새 승인을 막는 앱 측 예약과 네이티브
종료 확인은 별도로 연결해야 한다.

`1adf264`의 Windows·Linux·Android 코어와 APK 검사는 모두 통과했고,
정식 보안 검증은 이전과 같은 요청 항목 시간 초과로 실패했다. 별도 진단은

그 결과와 도구의 공식 상태 표현 지침을 바탕으로 모델 내부 표현을
조정했다. 역변환 시 기존 모델·공격 예제와 일치하는 검사는 통과했으며,
실제 정식 증명 결과는 다음 CI에서 확인해야 한다.

`61166a2`에서도 같은 요청 검증 시간 초과가 남았다. 후속 진단에서 생성

### 검증된 소스 범위: 휴대폰 등록 정보와 수신 연결

같은 저장 트랜잭션에 PC·수신 기기·등록 개정 번호·휴대폰 키·PC 공개키의
대응 관계를 추가했다. 실제 TCP/TLS 수신 경로가 그 관계와 앱 소유자 수명을
유지하도록 연결했다. 연결 취소·재등록·앱 소유자 재시작 뒤 이전 메시지 거절을
포함한 실제 loopback 테스트 8개가 양쪽 호스트 CI에서 통과했다.
등록 절차 자체와 실제 알림·인증·서명 연결은
아직 남아 있다. 로컬 키나 저장된 관계가 존재한다고 이 기능들을 켜지 않는다.

### 검증된 소스 범위: 요청의 최초 수신 정보 보존

요청마다 최초 등록 세대를 저장하고, 복구·재전송 시 이를 다른 세대로
바꾸지 않도록 했다. 이전 형식에 수신 정보가 없으면 현재 PC의 키를 추측해
채우지 않는다. 등록이 바뀐 요청의 본문은 보류하되 만료·철회 결과는 유지한다.
이 변경과 복구·재등록·만료 철회 회귀 테스트는 위 검증에 포함된다.
저장된 수신 정보 자체가 실제 인증 허가는 아니다.

### 검증된 소스 범위: 요청별 휴대폰 인증과 서명

원래 요청과 연결된 일회성 승인 계획, Android의 실제 CryptoObject 인증
작업, 서명·취소·화면 수명주기 처리를 추가했다. 기존 Application
작업 스레드와 키 소유자를 함께 사용한다. 서명 결과는 전송 전 준비 상태로만
분류하며 Windows 승인 성공으로 기록하지 않는다. 위 기준 커밋에서 모델·
연결부 테스트와 APK 빌드를 통과했다. 실제 등록·요청 수신·알림 게시·전송 연결과
사용자의 실제 휴대폰 인증 확인이 남아 있으며 설정 전용 시작 조건도 유지한다.

### 현재 작성 중: 실제 연결의 전송과 휴대폰 통신 키

승인 서명을 실제 소켓 전송에 연결하고, 대기·분할 전송 중 등록 해제나
요청 철회·서비스 기준 변경을 감지해 중단하도록 했다. 휴대폰의 기존 통신
키를 사용하는 정형 TLS 서명 연결부도 추가했다. 전송 대기와 로컬 소켓 쓰기는
Windows 승인 결과와 구분한다. 이 변경은 위 기준 커밋 검증에 포함되지 않는다.
네이티브 연결 시작·알림 서비스와 PC 쪽 수신·실행 연결은 아직 남았다.

이 단계에서는 파일을 삭제하지 않았다. 이후 사용자가 허가한 실험 전
공간 확보와 전체 작업 종료 후 정리는 위의 저장 공간 항목에서 구분한다.

## Android Application 소유자·실제 소켓 경로

Android에 한 개의 Application 작업자와 Rust 정책 소유자를 연결했다. Android
Tauri에서 이전 AppRuntime을 여는 경로는 제거했으며 Windows 경로는 유지했다.
기존 설정은 Tauri의 실제 dataDir 위치에서 읽고, 중단·손상·키가 남은 상태를
새 설치로 덮어쓰지 않는다. 알림 정리가 실패하면 종료 재시도 의무를 유지한다.
요청·인증·알림 수신 서비스가 완성됐다는 뜻은 아니다.

- 실제 arm64 Rust 라이브러리·새 Kotlin ABI 생성 성공.
- 생성 ABI, Application 작업자와 네이티브 어댑터의 Kotlin `-Werror` 컴파일,
  순수 JVM 검사 25개 통과. Tauri Kotlin 플러그인·전체 APK 검증은 별도다.
- Android용 Tauri Rust Clippy 통과. 호스트 Tauri 검사 5개와 Android 바인딩
  검사 14개, 표시/설정 런타임 검사 32개가 통과했다.
- 테스트 전용 소켓 루프를 production SocketDriver로 교체했다. 실제 TCP·중계·
  상호 TLS 경로 및 단편화·역압력·취소·기한·종료 검사 총 37개 통과.
  스택 고갈은 큰 상태/버퍼의 힙 소유로 수정했다. 겹치는 기한 두 검사에서는
  원래 제한을 그대로 둔 채 TLS 기한을 따로 검사하도록 시험 시각을 구분했다.
- 전체 workspace Clippy `-D warnings` 통과. 전체 Cargo/Analyzer와 플랫폼별 CI는
  현재 코드로 갱신해야 한다. 기존 중계 EOF 실패를 해결했다고 주장하지 않는다.

## CI 화면 확인으로 전환

사용자가 로컬 화면 승인을 놓친 상황을 설명하고 CI 갤러리 촬영을 지시했다.
로컬 앱/브라우저 접근을 다시 시도하지 않고 Windows·Linux CI에서 공유 React
클라이언트의 시험 화면을 촬영한다. 실제 UAC 승인과 휴대폰 인증은 사용자가
나중에 직접 확인하기로 했다. 이 수동 검증을 이미 통과한 것으로 표시하지
않으며, 이를 기다리느라 클라이언트 CI를 중단하지 않는다.

최상위가 실행한 화면 행동 테스트 21개, 빌드 분리 테스트 3개,
TypeScript·ESLint·제품/시험 빌드는 통과했다. 시험 출력은 고정 경로로 제한하며
제품 빌드에 시험 모듈이 섞이면 실패한다. 이어서 소스 `37890c7`의 실제 CI
실행 `34276434168`에서 Windows·Linux 각각 26개 시나리오가 통과했고 39장씩
촬영했다. ROOT가 다운로드해 대표 상태·경계 화면과 변경 이미지를 검토했다.
오류 예시가 빈 목록을 확정하던 모순과 촬영 도구의 오류 누락·결과 표시를 수정했다.

대표 원본 PNG 8장과 전체 갤러리 링크를 [이슈 #1](https://github.com/115dkk/Windows_UAC_Remote_Controller/issues/1)에 올렸다.
화면 코드·갤러리와 이미지 보관 커밋만 `codex/ci-ui-gallery`에 푸시했다.
main 병합·PR 생성·릴리스나 전체 Rust CI 성공은 아니다. 다른 Rust/Android 소스는
기존 로컬 작업 그대로 보존했다. 실제 CI·이미지 검토 기록은
`.superloopy/evidence/frontend/20260908T201702Z-ci-gallery/`에 있다.
이 브라우저 갤러리를 Tauri 설치·Secure Desktop·Android 인증의 증거로 쓰지 않는다.

## 최신 Android 연결 코드 단계

실제 arm64 Android Rust 라이브러리를 빌드하고, 그 라이브러리에서 Kotlin 연결
코드를 생성했다. 생성 코드와 Application 기반 네이티브 관측 어댑터는 Kotlin
1.9.25의 `-Werror` 컴파일을 통과했다. 네이티브 관측의 순수 테스트 12개,
Rust 연결부 호스트 테스트 5개, 빌드 도구 테스트 26개도 통과했다.

이 연결부는 **설정 전용 준비 단계**다. 요청 기록이 있는 저장소는 같은 잠금
안에서 먼저 거부하여 미구현 처리기가 만료 결과를 소모하지 않게 했다. 아직
Application/Service에 활성화하거나 기존 Tauri AppRuntime을 교체하지 않았다.
두 번째 Rust 라이브러리의 APK 배치, 시작 시 알림 정리, 요청·기록 처리기와
실제 인증 연결이 필요하다. Gradle 소스 생성/JNA 의존성은 선언했지만 전체
Gradle·APK 실행을 통과했다고 표시하지 않는다.

최신 전체 Rust 테스트는 **445개 통과·2개 실패**다. 중계의 연결 종료/기한
실패는 여전히 미해결이다. fmt·전체 Clippy·Android 대상 Clippy·실제 Rust
Analyzer는 통과했고 분석기의 조건부 컴파일 Hint 66개만 별도 기록했다.
호스트 전용 연결 코드 생성기는 호스트 전체 검사에 포함하며 Android 대상
검사에서만 Tauri 껍데기와 함께 명시적으로 제외한다. 실제 GitHub 실행은 아니다.

관련 기록: `.superloopy/evidence/android-binding-root-progress.md`,
`android-bindings-real-build-v3.txt`, `generated-native-controller-kotlin-v2.txt`,
`bindings-workspace-tests.txt`, `bindings-rust-analyzer.txt`.

## 최신 휴대폰 상태 저장·복구 단계

본문·명령어·개인키 없는 복구 형식, 중단 흔적을 남기는 파일 저장소,
저장 완료 후에만 결과를 반환하는 `DurableInbox`를 연결했다. 미처리 입력과
저장 완료된 폐기를 구분하며, 불확실한 저장이나 손상을 빈 상태로 초기화하지 않는다.

- 요청 코어 **54개**, 알림 복구 경계 **20개**, 저장소 **27개**, 실제 파일을
  사용하는 소유자 통합 **18개** 테스트가 최상위 실행으로 통과했다.
- 시간 밖 폐기 후 파일 재열기, 새 앱 실행을 깨운 요청, 원래 만료 시각 보존,
  재부팅·시계 불연속·복구 본문 재검증, 쓰기 실패 시 본문/표시 후보 차단을 확인했다.
- Rust 1.97의 표준 파일 잠금이 Android에서 지원되지 않는 문제를 확인했다.
  Android에서만 safe rustix API를 사용하도록 새 저장소와 기존 설정·기록 저장소를 수정했다.
- 전체 Clippy `-D warnings`, fmt와 실제 Rust Analyzer가 통과했다. 분석기 오류·경고는
  0개이며 조건부 컴파일 Hint 65개는 별도 기록했다. 실제 정상/오류/경고 판정 예제도 통과했다.
- Android 공통 Rust Clippy와 문서 테스트 6개가 통과했다. 백업 제외 XML은
  Android 빌드 도구로 리소스 컴파일만 확인했다. APK 포장·실기 동작 증거는 아니다.
- 최신 전체 Rust 테스트는 **438개 통과·3개 실패·제외 0개**다. 실패는 중계의
  대기 연결 종료, 반복 연결 세대 종료, 조기 입력 후 종료/기한 테스트다.
  기존 독립 Winsock 문제와 관련될 수 있으나 모든 실패의 원인이 같다고 단정하지 않는다.

따라서 G002/C001은 계속 fail이며 전체 제품은 미완료다. Windows 호스트의 파일
동기화 테스트를 Android의 전원 차단·디렉터리 동기화 증거로 쓰지 않았다.
실제 Android Application 소유자/바인딩, 알림·인증·등록 연결, 중단 저장소 복구와
기록 전달 보장은 남아 있다. [저장·복구 결정](adr/0004-phone-checkpoint-transactions.md)

## 최신 전송·안드로이드 소스 단계

현재 확장된 워크스페이스의 전체 품질 검사는 **실패**다. 슈퍼루피
G002/C001을 재실행해 fail로 갱신했다. 이전 단계의 통과 기록은 현재
중계·전송 코드까지 통과했다는 근거가 아니다. 현재 7개 목표 중 1개 완료,
14개 세부 기준 중 2개 통과이며 전체 제품은 미완료다.

- PC 서명 메시지·시각 대응(`service-protocol`), 상호 공개키 고정 TLS 1.3
  (`secure-channel`), 휴대폰 요청 수명주기(`phone-request-core`), 제한된
  프레임 운반(`framed-transport`), 불투명 TCP 중계(`relay-service`)를 추가했다.
- 새 클라이언트 연결 코드로 실제 로컬 중계와 상호 TLS를 거쳐 합성 PC 서명
  요청을 전달하는 통합 테스트가 통과했다. 클라이언트 연결·취소·기한·표식
  검사 5개도 통과했다. 인터넷·실제 기기·UAC 승인의 증거는 아니다.
- 휴대폰 요청 코어는 시계 오차에 따른 폐기 요청의 재등장 반례를 수정한 뒤
  42개 테스트와 Clippy가 통과했다. PC의 서명된 만료 확인 기록을 유지한다.
  프로세스 재시작 후 지속 저장·복원은 아직 구현하지 않았다.
- Windows의 연결 종료 테스트가 간헐적으로 실패한다. 중계/TLS/Tokio를
  제거한 독립 실험에서도 원시 Winsock 수준으로 재현했다. 원인은 미확정이며,
  제한 시간 연장·재시도·테스트 제외·시스템 설정 변경으로 통과시키지 않았다.
  별도 코드 감사에서 발견한 연결 인계 취소·상대편 조기 종료의 자원 수명주기
  결함 두 건은 수정했고, 최상위 실행 회귀 테스트 7개가 통과했다.
- UniFFI 0.32 실험은 Android 대상 `forbid(unsafe_code)` 유지 검사,
  실제 Android 공유 라이브러리 빌드와 Kotlin 바인딩 생성까지 통과했다.
  Kotlin/JNA의 실제 Android 실행은 입증하지 않는다.
- 새 Android 키 생성·검사 모듈은 Kotlin 1.9.25/API 36에서 `-Werror`
  컴파일과 순수 정책 테스트 10개를 통과했다. 승인·거절·연결용 키를 분리하고
  하드웨어 키와 승인용 요청별 인증 정책을 검사하는 소스다. 실제 키 생성,
  원격 인증서 검증, 승인 서명·생체/PIN 창, 등록 복구·폐기 처리는 아직 남았다.
- Android NDK 선택 도구 테스트 12개와 Android 공통 코어 Clippy를 추가 검증했다.
  최신 전체 품질 명령은 앞 단계의 중계 테스트에서 멈추므로 후속 분석기·라이선스
  단계까지 이번 전체 명령이 성공했다고 표시하지 않는다.
- 이후 개별 실행한 전체 Rust 테스트는 **362개 통과·2개 실패·제외 0개**였다.
  두 실패는 중계의 기다리는 연결 종료/기한 테스트다. 전체 Clippy, 문서 테스트
  6개, Android 공통 코어 Clippy는 통과했다. 실제 Rust Analyzer는 테스트의
  비동기 함수 호출에서 오류 3개로 실패했으나, 반환 Future의 Send 계약을
  컴파일러가 검증하도록 명시한 뒤 오류·경고 0개로 통과했다. 조건부 컴파일의
  inactive-code Hint 50개만 별도 기록하며 일반 진단은 제외하지 않았다.
  실제 정상/오류/경고 예제로 분석기의 실패 판정도 다시 확인했다.

## 이전 Windows·화면 통합 단계의 기록

공통 코어 뒤에 Windows 서비스 호스트, TPM 키 소유자, 화면용 런타임,
React 화면과 Tauri Windows/Android 호스트를 추가했다. 서비스 설치·키 생성·
실제 승인·페어링·전송·휴대폰 인증의 종단간 동작이 입증됐다는 뜻은 아니다.

- 화면의 strict TypeScript, ESLint(경고 0), 행동 테스트 21개, production 빌드가 통과했다.
- 새 Windows 통합에서 Rust 테스트 195개, 문서 테스트 5개, fmt와 전체 Clippy `-D warnings`가 통과했다.
- 실제 Rust Analyzer는 최초 통합에서 Tauri 생성 코드의 진단 25개로 실패했다. CLI의 dev cfg 일치와 실제 아이콘 배열 길이 보강 후 오류·경고 0개로 통과했다. 다른 cfg의 `inactive-code` LSP Hint 44개만 별도 기록하며 일반 진단은 제외하지 않았다. 실제 정상/오류/경고 예제로 실패 판정도 확인했다.
- 9월 9일 통합 품질 명령은 종료 코드 0이다. 분석기 환경/판정 Node 테스트 22개, Android 공통 코어 Clippy, 라이선스 메타데이터 471개 패키지도 검사했다. 별도 Android Tauri 라이브러리 Clippy `-D warnings`가 통과했다. APK·Kotlin·실기 검증을 뜻하지 않는다.
- Windows 실행 파일과 Android aarch64 Rust 라이브러리를 빌드했다. Windows cdylib 링크에는 한국어 MSVC 진행 문구를 경고로 취급하는 도구 문제가 남아 있다.
- Android APK 포장은 Windows 파일 링크 권한 부족으로 중단됐다. OS 보안 설정을 바꾸거나 다른 포장 방식으로 우회하지 않았다. Kotlin 단독 컴파일/JVM 테스트도 Gradle 캐시 이동 실패로 시작 단계에서 멈췄다. 작성한 Kotlin 테스트 8개는 아직 실행되지 않았다.
- 실제 Windows 앱과 localhost 화면의 자동 검사 권한이 모두 거부됐다. 다른 도구로 우회하지 않았고 시각·접근성·네이티브 동작을 통과로 표시하지 않았다.

## 반영한 사용자 결정

- 자격 증명형은 휴대폰에서 Windows 요구대로 입력하는 방법이 적절한지 평가한다. 적절하면 지원하고 무리가 있는 유형은 무시한다. Windows 인증을 앱 인증으로 대체하지 않는다.
- 이미 SYSTEM/커널이 침해된 경우는 위협 모델에서 제외한다. 일반 권한 악성코드가 이 서비스를 통해 상승하는 공격, 적대적 네트워크·중계, 미등록/폐기 기기는 계속 방어 대상이다.
- 모든 실행 검증은 최상위 에이전트가 했다. 구현·보안 감사 하위 에이전트는 코드/테스트 작성과 정적 검토만 했다.
- 마지막 `improve-codebase-architecture`의 승인자는 최상위 에이전트다. 새 리팩터링 에이전트의 후보 보고를 검토하고 승인한 안을 같은 에이전트에 되돌려 보낸 뒤 구현하게 한다. 사용자에게 밤중 승인을 요청하지 않는다.

## 첫 단계 Windows 실제 환경의 제한된 관찰

최상위가 `cargo run -p windows-observer --bin uac-observe --locked -- --once`를 실행했고 종료 코드 0이었다.

```text
platform=windows
process_session_id=1
thread_desktop=Default
input_desktop=Default
```

실제 UAC를 띄우거나 승인한 증거가 아니다. 이 과정에서 서비스 설치, 정책 변경, 데스크톱 전환, 화면 캡처, 입력 전송을 하지 않았다. 당시 관찰 모듈의 직접 작성한 unsafe 블록 **8개**는 Windows 전용 `src/ffi.rs`에 있다. 이후 서비스·키 크레이트에도 격리된 Windows FFI가 추가됐으며, 공통/Android/Tauri 소스는 unsafe를 금지한다. 종속/생성 코드 내부의 unsafe까지 0이라는 뜻은 아니다.

## 남은 필수 작업

1. 실제 UAC 요청 식별·최종 대상 결합과 자격 증명 입력 경로를 격리 환경에서 평가한다. Credential Provider의 기존 Windows 자격 증명 직렬화·자동 제출도 검토 후보이며, 앱 인증을 새 Windows 인증 방식으로 대체하는 별도 LSA 패키지를 뜻하지 않는다.
2. Windows 서비스·세션 보조 프로세스·TPM 키·ACL·매 QR 재발급 UAC·신뢰할 수 있는 페어링 절차.
3. 종단간 인증·암호화 전송 및 인터넷 중계/푸시, 재접속·기기 폐기·만료 신호.
4. Kotlin OS 연결, Android 요청별 인증·알림·일정 사전 검사·재시작 내구성·실기 지연 측정. SDK는 발견했지만 확인 시점에 연결된 adb 기기는 없었다.
5. 슈퍼루피 기반 Windows/Android Tauri React 화면과 플랫폼별 시각·접근성 검증.
6. 실제 GitHub CI 실행, main 연계 설치물 빌드·자동 릴리즈·서명·소스 제공.
7. 완성 결과의 보안 감사 및 **새 에이전트**를 통한 전체 아키텍처 리팩터링. 후보 보고 → 최상위 검토·승인 → 같은 에이전트에 승인안 재전달 → 구현 → 최상위 회귀 검증 순서로 진행한다.

커밋·푸시와 실제 GitHub Actions 검증은 진행했으며 최신 결과는 위에 기록했다.
PR·main 병합·릴리즈는 아직 수행하지 않았다. 전체 목표와 슈퍼루피의 나머지
기준은 미완료로 유지한다.

## 9월 12일 새벽: 프롬프트가 휴대폰까지 가고, 관리 파이프가 들어갔다

- 실제 관리자 권한 프롬프트가 휴대폰 요청이 되고, 휴대폰의 결정이 같은 창에 적용되는 통합(W10b)을
  검증해 올렸다. 워커 결과에는 ASTRA의 정적 검토가 짚은 결함이 있었고 모두 고쳤다. 시계 교환이 끝난
  연결에만 요청을 보내고, 프롬프트가 열린 뒤 접속한 휴대폰에는 같은 서명 요청을 한 번 다시 보낸다.
  엔진이 소비했거나 버린 요청은 곧바로 정리해 만료 단계와 어긋나지 않게 했다. 경로가 없는 프롬프트(MSI,
  COM 권한 상승, 패키지 앱)도 요청이 되도록 빈 경로를 허용했다.
- 실험실이 빠진 토큰 권한 하나(TOKEN_ADJUST_DEFAULT)를 찾아 헬퍼 실행 토큰 마스크를 고쳤다. 다음
  실행에서 헬퍼가 대화형 세션에서 떠 있고 실제 consent.exe가 12초 넘게 떠 있었는데도 관측 기록이 없었다.
  서비스가 감시 헬퍼를 잡고 있으면 probe-once는 바쁨으로 끝나므로 그 진단은 더 쓸 수 없다. 그래서
  서비스가 감시 헬퍼의 시작, 첫 심장박동, 재시작, 포기를 고정된 종류로만 활동 기록에 남기게 했고,
  실험실은 이제 활동 기록에 관측 기록이 있어야 통과한다. 헬퍼가 죽은 것인지, 살아서 창을 찾지 못하는
  것인지 다음 실행이 알려준다. 그런데 그 첫 실행에서는 다른 일이 벌어졌다. 관리 파이프(W9)가 실제 서비스에서
  처음 켜지자 서비스가 실행 상태에 들어간 1초 뒤 작업자 실패로 멈췄고, 감시 헬퍼는 시작도 못 했다. 관리 파이프는
  부가 기능이므로 다음 판부터는 켜지지 못해도 서비스가 계속 돌고, 활동 기록에 고정 종류로 남기며, 실험실 빌드는
  실패 이유를 메모에 적는다.
- 관리 파이프(W9)가 들어갔다. 서비스는 접속한 프로세스의 PID와 세션, 생성 시각, 설치된 실행 파일과의
  일치, 토큰, 세션 시대를 직접 확인한다. 설치된 일반 권한 GUI는 조회만 하고, 관리자 권한 CLI만 기기
  삭제와 중계 주소 설정을 한다. 기기 패널이 연결 상태와 함께 짝지은 휴대폰을 보여 주고 중계 주소를
  받는다. 워커 코드는 그대로 컴파일되지 않아(모듈 깊이, 재수출, 기기 id 직렬화, 바뀐 읽기 한도)
  루트가 고쳐 검증했다.
- Linux 품질 검사와 Android 코어 검사가 깨진 원인(감시 세션의 적용 seam이 Windows 전용 모듈을 참조)과
  Tamarin 게이트의 검토 소스 해시(빈 경로 변경)를 고쳤다. Android intake 테스트가 windows-2025에서만
  실패하던 경쟁도 고쳤다.
- 알파에 남기는 알려진 제한: 헬퍼의 적용 메시지에 원래 만료 시각이 없어 UI 자동화 호출이 느리면 110초
  뒤 같은 창에 적용될 수 있다. Android 등록 절차는 admission이 바쁠 때 일회성 객체를 잃어 다시 시작해야
  한다. 스캐너 계측 검사가 한 번 카메라 사용 불가로 실패했고 다음 실행에서는 통과했다. 개발 PC는 아직
  다시 시험하지 않았다(사용자가 미뤘다).
## 9월 12일 아침: 프리 릴리즈 v0.1.0-alpha.1 게시와 감시 헬퍼 진단

- 태그 v0.1.0-alpha.1을 처음 붙인 판(fae5d1f)에서는 Android 릴리스 APK 작업이 바인딩 생성 단계에서 멈췄다.
  릴리스 프로필의 `strip = true`가 UniFFI 메타데이터 심볼까지 지워 생성기가 메타데이터를 못 찾았고, CI는 그동안
  디버그 변형만 빌드해 드러나지 않았다. 디버그 정보만 지우도록 고치고(df85f03), 아직 게시된 릴리스가 없었으므로
  태그를 지우고 6551fcc에 다시 붙였다. 릴리스 워크플로(34646050609)가 Windows 설치 파일, 서명된 arm64 APK,
  Windows와 Linux 중계 서버, SHA256SUMS와 검사 파일을 프리 릴리즈로 게시했다. 게시는 패키징 사실일 뿐이고,
  릴리스 노트의 표에 무엇을 확인했고 무엇을 확인하지 못했는지 적었다.
- 실험실에서는 서비스 쪽이 정리됐다. 관리 파이프는 실험실 설치에 GUI 실행 파일이 없어 켜지지 않지만
  (OpenProtectedPath 0x80070002) 서비스는 계속 돌고, 감시 헬퍼는 시작해 심장박동을 보낸다. 실제 consent 창이 떠
  있는데도 관측이 없던 이유는 헬퍼에 실험실 전용 기록 기능을 넣은 뒤(6551fcc, 005d93e) 드러났다. Winlogon
  데스크톱에서 census가 최상위 창 열 개를 보았고 그중 여러 개가 consent.exe 소유여서 창이 떠 있는 동안 일흔 번
  연속 '모호함'으로 끝났다. consent.exe는 대화 상자 말고도 GUI 스레드마다 숨은 최상위 창(IME 창 등)을 가진다.
  보이는 창만 후보로 세도록 고쳤고(f9c9055), 다음 실험실 실행이 census가 대화 상자를 알아보는지 알려준다.
## 9월 12일 아침 7시: 감시 헬퍼가 실제 관리자 확인 창을 관측했다

- 헬퍼를 세 번 고쳤고, 매번 직전 실험실 기록이 다음 결함을 가리켰다. 보이지 않는 창(스레드마다 있는 숨은 IME
  창)을 후보에서 뺐고(f9c9055), UI 자동화 검사 실패를 헬퍼 종료가 아니라 그 주기의 판정으로 다루면서 소유된 창과
  도구 창, 활성화되지 않는 창(입력 표시기, 보안 배경 창)을 뺐다(26aa610). 마지막으로 패턴 가용성 속성을 공급자
  기본값으로 읽게 했다(fd300d1). XAML 기반 대화 상자는 패턴을 구현하지 않은 요소에 '지원 안 함' 객체를 돌려주는데
  엄격한 검사가 그것을 결함으로 보아 매 주기 대화 상자 전체를 거부하고 있었다.
- 그 뒤 실험실 실행(34650918887)이 통과했다. 호스팅 러너의 보안 데스크톱에 뜬 실제 consent.exe에서 census가
  `Credential Dialog Xaml Host` 창 하나로 정해지고, 헬퍼가 나타남을 보고하고, 서비스가 요청을 열어 활동 기록에
  관측을 남겼으며, 같은 창을 실험실이 닫을 때까지 64주기 동안 추적했다. 관측까지다. 등록된 휴대폰이 없어 요청을
  보내지도, 적용하지도 않았으므로 휴대폰 결정과 같은 창에 적용하는 단계는 실제 창에서 아직 확인하지 못했다.
- 이 수정들을 담아 v0.1.0-alpha.2를 낸다. 릴리스 노트 표에 실험실 관측 사실을 적었다.
