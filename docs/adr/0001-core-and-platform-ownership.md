# ADR-0001: Safe core, thin presentation, explicit platform ownership

Status: accepted for implementation, 2026-09-08.

## Context

The user requires Rust-owned service logic and Tauri/React presentation, with
Kotlin handling Android APIs without handwritten unsafe JNI where avoidable.
An attacker-controlled network or local user process must not gain an approval
or arbitrary execution interface. A core test cannot prove an OS integration.

## Decision

- `approval-protocol` owns bounded immutable request data and versioned signing
  bytes, key parsing and signature verification. It does not choose a Windows
  process to run, enroll devices, store private keys or claim transport secrecy.
- `approval-core` owns the trusted-host device registry, pending requests,
  lifetime and decision consumption. Its output is authorization to attempt an
  action, never a fabricated Windows success.
- `notification-policy` owns validated schedules and metadata-only notification
  lifecycle decisions. Actual Android delivery, authentication and persistent
  replay protection remain the native host's responsibility.
- `activity-journal` owns bounded operational history. It has no freeform secret
  payload and must not be used for authority state.
- The forthcoming Windows adapter owns native prompt identity and final action
  binding. Required unsafe FFI belongs there, behind owned lifetime-safe types.
- Android native code owns lock-state detection, request-bound Keystore operations,
  notification actions and background entry points. The reference app's
  Activity-based `run_mobile_plugin` pattern is evidence for a safe foreground
  bridge, not proof of process-terminated background operation.
- Tauri/React only presents service state and submits user intent. It must not
  hold approval private keys or impersonate a service authorization decision.

Shared, Android, transport and Tauri Rust forbid unsafe code. The implemented
Windows observer, key owner and service host deny it by default and allow it only
in their explicitly scoped Windows FFI/SCM entry modules, with per-operation
ownership and safety invariants. No such module is linked into Android. Generated
and dependency code is reported separately, not presented as an unsafe-free
binary or dependency graph.

## Consequences

Core interfaces can be tested without changing Windows policy or using real
credentials. Privileged-host and native adapters must still be tested against
the complete product requirements. A registry populated in a test is not a
paired phone; a signature generated by a test fixture is not Android biometric
authentication; a Rust target check is not a working Android application.
